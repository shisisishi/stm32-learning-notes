## 2. 原理：它到底是怎么工作的

### 2.1 为什么不能用纯文本协议

`printf("%d,%d\r\n", target, actual)` 这句话看起来没有任何问题，但把它放到
1 kHz 的控制回路上，问题就一个一个冒出来了。

假设 `target = 2000, actual = 1987`，发出去的是这 12 个字符：

```text
'2','0','0','0',',','1','9','8','7','\r','\n'   →  共 11 字节
```

| 问题 | 具体表现 |
|---|---|
| **变长** | `actual` 是 3 时这一行只有 8 字节，是 1234 时 11 字节。接收端没法靠"固定长度"切帧，只能靠 `\r\n` 找行尾 |
| **解析慢** | 上位机要逐字符扫描、找逗号、找换行，再把 `"1987"` 这 4 个字符**乘 10 累加**变成整数。用 C 是 `sscanf`/`atoi`，用 Python 是 `int()` —— 都是字符串到数字的完整转换流程 |
| **没有同步机制** | 如果串口上还夹着别的调试输出（比如一个 `printf("init ok\r\n")`），上位机那一行就解析失败了；丢了半个字节，后面整行都是错的，而且**错得没有提示** |
| **字节数大** | 11 字节只是两个 `int16` 的数据量（4 字节）。带上 `\r\n`、逗号，开销超过 150% |
| **没有校验** | 传输中被干扰了一位，接收端完全不知道，会把 `1987` 当成 `1983` 画到曲线上，然后你开始怀疑自己的 PID 参数 |

算一笔带宽账：115200 8N1 的情况下，每字节占 10 位（1 起始 + 8 数据 + 1 停止），
所以有效速率是

```text
115200 / 10 = 11520 字节/秒
```

- 文本协议：一帧 11 字节 → `11520 / 11 ≈ 1047 行/秒`，理论值看着够。

  但这是**串口线上**的账，没算单片机这边。`printf` 走的是阻塞发送，
  在 72 MHz 的 F103 上把 11 个字节塞进 `DR` 寄存器、每个字节等发送完成，
  11 × 87 µs ≈ **0.96 ms**。而我 1 kHz 的控制周期总共只有 1 ms。
  也就是说：**光把这一行打印出去，控制周期就用完了**，PID 计算本身还没开始。
  这就是第 6 节那个坑的根因。

- 二进制协议：一帧 12 字节装 3 个 `int16`（6 字节数据），
  同样 11520 字节/秒 → `11520 / 12 = 960 帧/秒`。
  而且解析不需要字符串转换，上位机拿到 6 个字节直接按小端拼成整数就行。

### 2.2 二进制帧协议的设计

要让接收端能从一串连续的字节流里**自己找到每一帧的边界**，需要几个各司其职的字段。
我用的格式是（小端，定长头 5 字节 + 变长载荷 + 1 字节校验）：

```text
偏移  0    1    2     3     4     5 .. 5+N-1   6+N
     +----+----+-----+-----+-----+-----------+------+
     | A5 | 5A | LEN | SEQ | CMD |  PAYLOAD  | CRC8 |
     +----+----+-----+-----+-----+-----------+------+
       SOF(2B)  1B    1B    1B      N 字节       1B
```

| 字段 | 偏移 | 长度 | 作用 | 为什么需要它 |
|---|---|---|---|---|
| 帧头 SOF | 0, 1 | 2 字节（`0xA5 0x5A`） | 找同步点 | 接收端从任意位置开始扫，扫到 `A5 5A` 就认为"这可能是帧的开头"。没有它，接收端不知道哪 6 个字节才是定长头 |
| 长度 LEN | 2 | 1 字节 | 知道还要收多少 | 载荷是变长的（PID 数据 6 字节、调试文本可能 20 字节）。没有它，接收端只能靠"等一个固定时间没收到新字节"来判断帧结束，一旦波特率抖动或中断延迟就会切错 |
| 序号 SEQ | 3 | 1 字节 | 检测丢帧 | 接收端看序号是不是从 0x07 跳到 0x09，就知道中间丢了一帧。调 PID 时如果中途丢帧，曲线上会出现假跳变，你会误以为是控制器在震荡 |
| 命令字 CMD | 4 | 1 字节 | 区分数据类型 | 同一条串口上要传 PID 数据、参数下发、调试文本……接收端靠它决定把载荷按什么结构解释。没有它就只能开多条串口 |
| 载荷 PAYLOAD | 5 ~ 5+N-1 | N 字节 | 实际数据 | 前面 5 个字节都是"为了把数据送到"付出的开销，真正的信息在这里 |
| 校验 CRC8 | 6+N | 1 字节 | 检错 | 传输误码、干扰、甚至半个字节的错位，都靠它拦下来。宁可丢掉一帧，也不能把错误数据画到曲线上 |

N = 6 的时候（三个 `int16` 的 PID 数据），总长度是 12 字节，开销 6 字节 = 50%。
看着不便宜，但相比文本协议的 11 字节装 4 字节数据（开销 175%），还是省了一半以上。

### 2.3 为什么帧头要两个字节，而且不能是 0x00 / 0xFF

我第一版只用了单字节 `0xAA`，结果是：载荷里随便出现一个 `0xAA`，接收端就以为新帧开始了。

算一下概率：如果载荷的字节是均匀随机的，单字节帧头撞上的概率是 `1/256 ≈ 0.39%`。
一帧 6 字节载荷，一秒钟 1000 帧 → 每秒有约 `1000 × 6 × 0.39% ≈ 23` 次误同步。
每误同步一次，就要走一遍"读长度 → 收载荷 → CRC 失败"的流程，把真正的帧边界冲掉。

换成两个字节 `A5 5A` 之后，随机数据撞上这一对字节的概率是 `1/65536 ≈ 0.0015%`，
一秒钟的误同步期望降到 `1000 × 6 / 65536 ≈ 0.09` 次，也就是大约 11 秒一次，
而且**每次误同步都能被 CRC 拦下来**（不会输出错数据，只是浪费一点解析时间）。

为什么帧头字节特意选 `0xA5 / 0x5A` 而不是 `0x00 / 0xFF`：

| 候选 | 为什么不好 |
|---|---|
| `0x00` | 上电瞬间、线没接好、缓冲区清零，读到的全是 `0x00`。用 `0x00` 当帧头会把"线路断开"误判成"帧头出现"，然后一直等一个永远不来的 `LEN` |
| `0xFF` | 串口空闲时（比如 USB-TTL 拔掉），很多芯片的接收寄存器读出来是 `0xFF`；同理，浮空引脚也常读成 `0xFF` |
| `0xA5 / 0x5A` | 二进制是 `10100101` 和 `01011010`，是**互补**的一对，位模式交替得比较均匀。载荷里大量出现的连续 0、连续 1、或者递增序列（`0x01 0x02 0x03`）都不容易撞上它 |

这里要说清一个容易混淆的点：**两个字节帧头不能保证"绝不误同步"**，
它只是把概率降了 256 倍，并且给了 CRC 一个兜底的机会。
真正让解析健壮的不是帧头本身，而是下面这个状态机。

### 2.4 状态机解析器

"先找帧头、再 `memcpy` 一段出来解析"这种朴素写法有个死穴：
它假设**一帧数据是完整到达的**。而串口一次中断可能只收到半个帧，也可能一次收到两个帧。

解决办法是**逐字节喂的状态机**：每收到一个字节，就看一眼"当前处在哪一步、这个字节合不合法"，
然后决定下一步去哪。它天然不需要"一帧完整"这个前提。

```text
                    ┌──────────────────────────────────────────┐
                    │            非法字节 / 校验失败           │
                    ▼                                          │
            ┌───────────────┐                                  │
   任意字节 │ WAIT_SOF1     │ 收到 0xA5 ┌───────────────┐        │
  ─────────▶│ 找第一个帧头  ├──────────▶│ WAIT_SOF2     │        │
            └───────────────┘           │ 等第二个帧头  │        │
                    ▲                   └───────┬───────┘        │
                    │                    0x5A   │   非 0x5A      │
                    │                           ▼                │
                    │                   ┌───────────────┐        │
                    │                   │ READ_LEN      │◀──┐    │
                    │                   │ 读长度 LEN    │   │    │
                    │                   └───────┬───────┘   │    │
                    │              LEN ≤ 32     │  LEN > 32 │    │
                    │                           ▼           │    │
                    │                   ┌───────────────┐   │    │
                    │                   │ READ_BODY     │   │    │
                    │                   │ 收 2+N 字节   │   │    │
                    │                   │ (SEQ+CMD+载荷)│   │    │
                    │                   └───────┬───────┘   │    │
                    │              收满 2+N 字节 │           │    │
                    │                           ▼           │    │
                    │                   ┌───────────────┐   │    │
                    │        CRC 通过   │ VERIFY        │   │    │
                    └───────────────────┤ 核对 CRC8     │───┘    │
                        CRC 失败        └───────┬───────┘        │
                                                │ CRC 通过       │
                                                ▼                │
                                        ┌───────────────┐        │
                                        │ 回调 on_frame │────────┘
                                        │ 回到 WAIT_SOF1│
                                        └───────────────┘
```

五个状态的职责：

| 状态 | 在等什么 | 收到什么就去哪 |
|---|---|---|
| `WAIT_SOF1` | 帧头第 1 字节 | 是 `0xA5` → `WAIT_SOF2`；其他 → 留在原地 |
| `WAIT_SOF2` | 帧头第 2 字节 | 是 `0x5A` → `READ_LEN`；是 `0xA5` → 留在 `WAIT_SOF2`；其他 → 回 `WAIT_SOF1` |
| `READ_LEN` | 长度字段 | `LEN ≤ 32` → `READ_BODY`（要收 `2+LEN` 字节）；`LEN > 32` → 判为假帧头，回 `WAIT_SOF1` |
| `READ_BODY` | 序号 + 命令 + 载荷 | 收满 `2+LEN` 字节 → `VERIFY` |
| `VERIFY` | 校验字节 | 对得上 → 回调出这一帧，回 `WAIT_SOF1`；对不上 → 丢帧，回 `WAIT_SOF1` |

有两个细节值得单独说，因为它们是最容易写错的地方：

**细节一：`READ_LEN` 发现长度越界时要回到 `WAIT_SOF2`（如果当前字节正好是 `0xA5`）。**
想一下这个字节流：`A5 5A A5 5A ...`（载荷里正好有一对帧头时的情形）。
接收端在偏移 0 处认了帧头，读到偏移 2 的 `0xA5` 当长度 —— `0xA5 = 165 > 32`，越界了。
但**偏移 2 的这个 `0xA5` 有可能真的是下一帧的帧头第一个字节**。
如果直接回 `WAIT_SOF1`，就把它丢掉了，会漏掉一帧。
所以判越界的时候要多看一眼"这个越界字节本身是不是 `0xA5`"。

**细节二：CRC 的校验范围从偏移 0 开始，而不是从载荷开始。**
如果只校验载荷，那么长度字段被干扰时（`LEN` 从 6 变成 7），
CRC 照样能通过 —— 因为载荷本身没变。接收端就会按 7 字节去切帧，
把下一帧的第一个字节当成自己的载荷尾巴，后面全乱。
把帧头、`LEN`、`SEQ`、`CMD`、载荷**全部**纳入校验范围，这个问题就不存在了。

### 2.5 校验方式对比

| 方式 | 实现代价 | 能检出什么 | 检不出什么 | 适用场景 |
|---|---|---|---|---|
| **累加和**（把字节相加取低 8 位） | 最省，一个循环加法 | 单个字节的值错误 | **两个字节互换位置**（和不变）、两个字节误差互相抵消 | 对可靠性要求很低的场合 |
| **异或校验** | 一个循环异或 | 奇数个位错误 | 偶数个位错误（两个字节同一位一起翻） | 简单命令帧 |
| **CRC8**（多项式 `0x07`） | 每字节 8 次循环移位 | 全部 1 位错、全部 2 位错（在帧长 ≤ 127 字节内）、全部奇数位错、长度 ≤ 8 的突发错 | 极低概率的特定多位错误 | **本章选的方案** |
| **CRC16-CCITT**（多项式 `0x1021`） | 约 CRC8 的两倍 | 上面全部，且检错能力更强（帧长 ≤ 2048 字节的 2 位错） | — | 帧长几百字节以上的场合（MAVLink v1 用的就是它） |

为什么我选 CRC8 而不是 CRC16：我的帧最长只有 38 字节，CRC8 对 127 字节以内的
帧能保证检出任意的 1 位错和 2 位错，这个强度已经够；省下来的 1 个字节和多出来的
运算时间留给 1 kHz 的循环更有意义。

CRC8 的两种写法：

```c
/* 写法一：查表法。256 字节的表，运行时每字节只查一次表 —— 最快，但要占 256 字节 Flash */
static const uint8_t CRC8_TABLE[256] = { /* ... 上电时用下面的逐位法生成，或者直接常量表 ... */ };

uint8_t crc8_table(const uint8_t *data, size_t len)
{
    uint8_t crc = 0x00u;
    for (size_t i = 0u; i < len; i++) {
        crc = CRC8_TABLE[crc ^ data[i]];
    }
    return crc;
}
```

```c
/* 写法二：逐位法。不占表空间，代码短，我实际用的是这个 */
uint8_t crc8_bitwise(const uint8_t *data, size_t len)
{
    uint8_t crc = 0x00u;           /* 初值 0x00 */
    for (size_t i = 0u; i < len; i++) {
        crc ^= data[i];            /* 当前字节异或进寄存器 */
        for (uint8_t bit = 0u; bit < 8u; bit++) {
            if (crc & 0x80u) {
                crc = (uint8_t)((crc << 1) ^ 0x07u);  /* 最高位是 1：左移后异或多项式 */
            } else {
                crc = (uint8_t)(crc << 1);            /* 最高位是 0：只左移 */
            }
        }
    }
    return crc;
}
```

**为什么逐位法在 1 kHz 下也够用**：算一笔账。
一帧 11 个字节要校验，每个字节 8 次循环 = 88 次循环，每次循环里是
"判断最高位 + 左移 + 可能的异或"，在 Cortex-M3 上大约 5~8 个时钟周期。

```text
88 次 × 8 周期 ≈ 704 周期
704 / 72 MHz ≈ 9.8 µs
```

1 kHz 的周期是 1000 µs，CRC 占 **1% 左右**。
换查表法能省到约 2 µs，省下的 8 µs 对 1000 µs 的周期来说感知不到，
所以我选了不需要占 256 字节 Flash、代码更容易看懂的逐位法。
（这里说的是 `-O2` 下的量级估算，🔬 真实周期数要用 DWT 计数器或逻辑分析仪量。）

### 2.6 大小端与结构体对齐陷阱 ⚠️

这一节是我栽得最惨的地方，写清楚。

**第一个问题：字节序（endianness）**

`int16_t` 的 2000 在内存里是两个字节。小端（little-endian）存法是低字节在前：

```text
2000 = 0x07D0
小端：D0 07      ← STM32（Cortex-M3）是小端，x86 PC 也是小端
大端：07 D0      ← 某些网络协议、部分 DSP 是大端
```

STM32 和 PC 都是小端，所以"原样把字节发过去，PC 原样拼回来"是成立的。
但**上位机如果用 Python，`struct.unpack` 一定要显式指定字节序**：

```python
import struct
# '<hhh' 里的 '<' 就是"小端、标准大小"
setpoint, actual, output = struct.unpack('<hhh', payload)
```

不写 `<` 的话，`struct` 会用**本机字节序**（`@`），在 x86 上碰巧也是小端所以能跑。
但这属于"靠平台的巧合活着"——哪天把上位机搬到 ARM 服务器或者别的架构上就跑不通了。
显式写 `<` 是零成本的保险。

**第二个问题：结构体对齐（这是真正会出错的）**

C 编译器为了访问效率，会让结构体成员按照自己的大小对齐。
`uint16_t` 要求地址是 2 的倍数，`uint32_t` 要求 4 的倍数。
所以你写：

```c
struct Demo {
    uint8_t  a;    /* 1 字节 */
    uint16_t b;    /* 2 字节，但它要求起始地址是 2 的倍数 */
};
```

编译器会在 `a` 后面**塞 1 个填充字节**，让 `b` 从偏移 2 开始：

```text
实际内存布局（默认对齐）：
偏移 0    1        2    3
     +----+--------+----+----+
     | a  | 填充   | b 低 | b 高 |
     +----+--------+----+----+
sizeof = 4，而不是 3
```

我第一版就是这么写的 PID 数据结构（`uint8_t seq; uint32_t timestamp; int16_t data[3];`），
然后用 `memcpy(buf, &my_struct, sizeof(my_struct))` 直接往串口发。
上位机按"偏移 0 是 seq、偏移 1 开始是 timestamp"解包，**从第 2 个字段开始全错位**，
解出来的时间戳是天文数字，数据是垃圾。

解决办法有两个，我更推荐第二个：

```c
/* 办法一：加 packed 属性，告诉编译器"不要填充" */
#if defined(__GNUC__) || defined(__clang__)
    #define PROTO_PACKED __attribute__((packed))
#elif defined(_MSC_VER)
    #pragma pack(push, 1)
    #define PROTO_PACKED
#endif

typedef struct PROTO_PACKED {
    uint8_t  a;
    uint16_t b;
} DemoPacked;      /* sizeof == 3，b 在偏移 1 */
```

```c
/* 办法二（我更推荐的）：根本不用结构体去对齐内存，
 * 而是老老实实按字节偏移往 uint8_t 数组里写。
 * 这样上下位机的"第几个字节是什么"是写死在代码里的，跟编译器版本无关。 */
out[0] = PROTO_SOF1;
out[1] = PROTO_SOF2;
out[2] = payload_len;
out[3] = seq;
out[4] = cmd;
```

为什么更推荐办法二：`packed` 结构体虽然能让 `sizeof` 变对，但
**读一个 packed 结构体里未对齐的 `uint32_t` 成员，在 Cortex-M0 上会触发硬件异常**
（M3 支持非对齐访问，所以 F103 上碰巧没事，一换芯片就炸）。
而且 `packed` 是编译器扩展，不是 C 标准的一部分，换编译器要重新配。
我的做法是：**打包/解包一律按字节偏移手写，结构体只用来组织解析器内部的状态。**

**怎么验证自己有没有踩这个坑**：

```c
/* 最直接的办法：把 sizeof 和 offsetof 打印出来，和"你以为的"对一遍 */
printf("sizeof(Demo) = %u\r\n", (unsigned)sizeof(Demo));
printf("offsetof(Demo, b) = %u\r\n", (unsigned)offsetof(Demo, b));
```

我在 `code/protocol/test_protocol.c` 的第 9 组测试里就把这个打印出来了，
让它成为**回归测试的一部分**，而不是靠眼睛看一遍代码。

### 2.7 环形缓冲区 + 状态机：为什么不直接在中断里跑状态机

串口接收中断（USART1_IRQHandler）里能做的事应该尽量少。
我的分工是：

```text
     USART1 接收中断                     主循环
   ┌──────────────────┐            ┌──────────────────────┐
   │ 读 DR 拿 1 字节  │            │ 从环形缓冲取 1 字节  │
   │ 塞进环形缓冲区   │───────────▶│ 喂给状态机           │
   │ 立刻返回         │  环形缓冲  │ 解析成功后更新数据   │
   └──────────────────┘  (256 字节)│ 攒够一批去绘图/发上位机│
         ~1 µs                    └──────────────────────┘
```

中断里只做"取一个字节、存一个字节"，大概几十个时钟周期；
耗时的解析、CRC、回调、绘图全放主循环。

如果在中断里直接跑状态机和 CRC，会有三个麻烦：

1. **中断时间变长**。1 kHz 下每 1 ms 就有 12 个字节要到，中断一次跑几十微秒的话，
   中断本身的进出开销（保存/恢复寄存器）就占掉可观比例，挤占 PID 计算的执行时间。
2. **字节会丢**。串口的接收寄存器（`USART_DR`）只能存 1 个字节。
   中断处理得慢了，下一个字节到了而 `DR` 还没被读走，就会置位溢出标志（`ORE`），这个字节就没了。
3. **在主循环里没法做"一批处理"**。绘图要每 10 ms 更新一次屏幕，
   如果把解析放在中断里，主循环只能被动地"来一帧画一帧"，反而更容易卡。

环形缓冲区本身不复杂，三个要点：`head` 只在中断里动、`tail` 只在主循环里动
（这样单生产者单消费者不需要加锁）、满的时候**丢掉新数据而不是覆盖老数据**
（覆盖老数据会让状态机收到顺序错乱的字节，直接解析崩掉）。

🔬 上面这套分工的实测数据（丢包率、中断耗时）要等板子和 USB-TTL 到了才能给，
现在写的是设计意图和预期现象。

### 2.8 半包 / 粘包：状态机方案的最大优势

这是状态机相对于"等一帧收完再解析"的核心优势，单独说。

**半包**：串口一次中断只收到了半个帧。

```text
第 1 次到达（6 字节）: A5 5A 06 01 01 D0
第 2 次到达（6 字节）: 07 68 01 2C 01 4F
                      ↑ 这里才是载荷的第 2 个字节
```

朴素写法的做法是"先 `memcpy` 一段到缓冲区，再找 `A5 5A`"——
它必须猜"一段有多长"，猜 12 字节就正好，猜 8 字节就切错了。
状态机不猜：它收到第 6 个字节的时候停在 `READ_BODY`、`index = 1`
（已经存了 1 个载荷字节），静静等着；第 7 个字节一到就接着存。
**半包对状态机来说不是"异常情况"，就是最正常的情形。**

**粘包**：一次中断收到了两个帧（主循环一次从环形缓冲里取出了两帧的全部字节）。

```text
A5 5A 06 07 01 [01 00 02 00 03 00] 8F  A5 5A 04 08 03 [AA BB CC DD] 6E
└────────── 第 1 帧（12 字节）──────┘  └────────── 第 2 帧（10 字节）─┘
```

状态机在第 1 帧的 `VERIFY` 通过、回调出去之后，直接把状态置回 `WAIT_SOF1`，
下一个字节 `A5` 被当作新帧头处理，接着解析第 2 帧。**粘包同样不需要特殊处理。**

我的自测程序第 4 组用例就是**穷举所有切分点**：把一帧 12 字节的数据从第 1 个字节后切开、
从第 2 个字节后切开……一直到第 11 个字节后切开，每一种都要能解出来；
还额外测了"一个字节一个字节喂"这种极端情况。第 5 组用例测的是粘包。
这两组用例是我写完解析器之后最先补上的，因为它们是"要么全对、要么在某些切分点悄悄出错"的类型，
靠手动测试根本覆盖不全。

### 2.9 上位机可视化

PC 这边用 Python + pyserial 读串口，`struct` 解包，然后画图。
选 `pyqtgraph` 还是 `matplotlib`：

| | matplotlib | pyqtgraph |
|---|---|---|
| 每帧重绘机制 | 重建整个 Figure，开销大 | 复用 `PlotDataItem`，只更新数据 |
| 1 kHz 数据实测观感 | 明显卡顿、越跑越慢 | 流畅 🔬 |
| 画静态图/导出 PNG | 好看，文档多 | 一般 |
| 学习成本 | 低 | 中（要了解 Qt 的 `QTimer`） |

我的用法是：**调试时用 pyqtgraph 看实时曲线，导出报告图用 matplotlib**。

为什么二进制协议能画 1000 个点而文本协议只能画 50 个：

| | 文本协议 | 二进制协议 |
|---|---|---|
| 每帧字节数（3 个 `int16`） | ≈ 17 字节（`"2000,1987,1234\r\n"`） | 12 字节 |
| 115200 8N1 下每秒最多 | 11520 / 17 ≈ **677 帧** | 11520 / 12 = **960 帧** |
| 单片机能承受的发送频率 | 实测约 300~500 Hz 就开始拖慢控制周期（`printf` 阻塞） | 1 kHz 时发送占用的时间约 12 字节 × 87 µs ≈ 1.0 ms，**也快满了** |
| 上位机解析开销 | 每帧要做字符串→整数的转换，Python 里约 5~10 µs | `struct.unpack` 一次约 0.5 µs |

这里我要说清楚一件事：**1 kHz 数据并不等于要靠 115200 波特率硬扛**。
更合理的做法是**降采样**——PID 还是 1 kHz 在跑，但每 10 个周期才发一帧（100 Hz）。
调试观察曲线用 100~200 Hz 完全够了，还能给控制循环留出余量。
（如果真的需要全速上传，F103 的 USART1 可以跑 460800 甚至 921600，
那是另一个话题，🔬 待实测。）

### 2.10 CAN 总线：同样的打包思路

RoboMaster 的电机（M3508 减速电机、M2006、GM6020）走的是 **CAN 总线（Controller Area Network）**，
不是串口。CAN 的报文数据段**最多 8 字节**，而且电机厂商把
"转速、电流、角度"这些量定义成 8 个字节里的固定位置。

以我目前查到的资料，M3508 电调（C620）的反馈报文长这样（🔬 需要对着官方
《RoboMaster 电机驱动使用说明》核一遍再写进笔记，这里写的是我理解的结构）：

```text
CAN 帧，ID = 0x201（1 号电机反馈），DLC = 8
字节  0    1    2    3    4    5    6    7
    +----+----+----+----+----+----+----+----+
    | 机械角度(0~8191) | 转速(rpm) |  电流   | 温度 |
    +----+----+----+----+----+----+----+----+
     16 bit 小端      16 bit 小端  16 bit  8 bit
```

看这个布局的每一个字段：给定位宽、定偏移、小端、需要"打包"和"解包" ——
**这就是本章在做的事情，只是搬到了 CAN 上，总线从串口换成了 CAN 而已。**

所以学这一章的收益不只是串口：

| 本章学到的东西 | 在 CAN 上怎么用 |
|---|---|
| 按字节偏移读写定长字段 | 解析电机反馈的 8 字节报文 |
| 小端拼 `int16`（`low | (high << 8)`） | 从 2 个字节还原转速，再乘减速比换算成实际转速 |
| 校验/边界意识 | CAN 硬件层自带 CRC 和自动重发，所以报文里不用再放校验字段 —— **理解"为什么要校验"才能判断"什么时候不需要校验"** |
| 状态机 + 缓冲区 | CAN 接收用 FIFO + 中断，思路和环形缓冲一致 |

这一点对我很重要：**RM 的电控代码里，电机通信是最基础的一块**，
海报上「机器人组件间的通信」说的主要就是这件事。

### 4.1 `protocol.h`（帧格式与接口）

```c
/* 帧头（SOF，Start Of Frame）。故意选两个字节：单字节帧头太容易在载荷里撞上。 */
#define PROTO_SOF1              0xA5u
#define PROTO_SOF2              0x5Au

/* 最大载荷。上位机一次要 4 路数据，每路 2 字节，留到 32 字节已经够用；
 * 解析器内部缓冲区按这个值静态分配，不动态申请内存。 */
#define PROTO_MAX_PAYLOAD       32u

/* 定长部分：2 字节帧头 + 1 字节长度 + 1 字节序号 + 1 字节命令 + 1 字节校验 */
#define PROTO_OVERHEAD          6u

#define PROTO_CMD_PID_DATA      0x01u   /* PID 运行数据：目标/实际/输出，各 int16 */
#define PROTO_CMD_DEBUG_TEXT    0x02u   /* 调试文本，载荷是一串 ASCII */
#define PROTO_CMD_SET_PARAM     0x03u   /* 上位机下发参数：参数号 + float 值 */
#define PROTO_CMD_ACK           0x04u   /* 从机应答 */

/* 解析器状态机的五个状态 */
typedef enum {
    PROTO_ST_WAIT_SOF1 = 0,  /* 找第一个帧头字节 0xA5 */
    PROTO_ST_WAIT_SOF2,      /* 收到 0xA5，等第二个帧头字节 0x5A */
    PROTO_ST_READ_LEN,       /* 读长度字段 */
    PROTO_ST_READ_BODY,      /* 收序号 + 命令 + 载荷（共 2+N 字节） */
    PROTO_ST_VERIFY          /* 读并核对 CRC */
} ProtoState;

/* 一帧解析完成时的回调。payload 指向解析器内部缓冲区，要留存就自己 memcpy 走 */
typedef void (*ProtoFrameCallback)(uint8_t cmd, uint8_t seq,
                                   const uint8_t *payload, uint8_t len);

typedef struct {
    ProtoState state;                        /* 当前状态 */
    uint8_t    buf[PROTO_MAX_PAYLOAD + 2u];  /* 存 序号 + 命令 + 载荷 */
    uint8_t    index;                        /* buf 里已存了多少字节 */
    uint8_t    need;                         /* 这一帧 buf 里总共要存多少字节 */
    uint8_t    len;                          /* 本帧载荷长度 */
    uint8_t    seq;                          /* 本帧序号 */
    uint8_t    cmd;                          /* 本帧命令字 */
    uint32_t   crc_error_count;              /* 校验失败次数，掉线时看这个 */
    uint32_t   frame_count;                  /* 解析成功的帧数 */
    ProtoFrameCallback on_frame;             /* 回调，可为 NULL */
} ProtoParser;

uint8_t  Protocol_Crc8(const uint8_t *data, size_t len);
uint8_t  Protocol_Crc8Continue(uint8_t crc, const uint8_t *data, size_t len);
size_t   Protocol_Pack(uint8_t *out, size_t out_size,
                       uint8_t cmd, uint8_t seq,
                       const uint8_t *payload, uint8_t payload_len);
void     Protocol_Init(ProtoParser *p, ProtoFrameCallback cb);
void     Protocol_Reset(ProtoParser *p);
ProtoStatus Protocol_ParserFeed(ProtoParser *p, uint8_t byte);
uint32_t Protocol_ParserFeedBuffer(ProtoParser *p, const uint8_t *data, size_t len);
```

### 4.2 `protocol.c` 的核心：CRC 与打包

```c
uint8_t Protocol_Crc8Continue(uint8_t crc, const uint8_t *data, size_t len)
{
    size_t  i;
    uint8_t bit;

    if (data == NULL) {
        return crc;      /* 没有数据就原样返回，不会把已有结果清零 */
    }

    for (i = 0u; i < len; i++) {
        crc ^= data[i];                 /* 当前字节异或进 CRC 寄存器 */
        for (bit = 0u; bit < 8u; bit++) {
            if ((crc & 0x80u) != 0u) {
                crc = (uint8_t)((crc << 1) ^ 0x07u);   /* 最高位是 1：左移后异或多项式 */
            } else {
                crc = (uint8_t)(crc << 1);             /* 最高位是 0：只左移 */
            }
        }
    }
    return crc;
}

/* CRC 的初值就是 0x00，所以"从头算"等于"从 0x00 接着算" */
uint8_t Protocol_Crc8(const uint8_t *data, size_t len)
{
    return Protocol_Crc8Continue(0x00u, data, len);
}

size_t Protocol_Pack(uint8_t *out, size_t out_size,
                     uint8_t cmd, uint8_t seq,
                     const uint8_t *payload, uint8_t payload_len)
{
    size_t total;
    size_t i;

    if (out == NULL)                              { return 0u; }
    if (payload_len > PROTO_MAX_PAYLOAD)          { return 0u; }  /* 宁可不发也不发半帧 */
    if ((payload_len > 0u) && (payload == NULL))  { return 0u; }

    total = (size_t)PROTO_OVERHEAD + (size_t)payload_len;
    if (out_size < total)                         { return 0u; }  /* 输出缓冲区放不下 */

    /* --- 定长头：按字节偏移手写，不用结构体，避免对齐填充的坑 --- */
    out[0] = PROTO_SOF1;                 /* 偏移 0 */
    out[1] = PROTO_SOF2;                 /* 偏移 1 */
    out[2] = payload_len;                /* 偏移 2：长度 = 载荷字节数 */
    out[3] = seq;                        /* 偏移 3 */
    out[4] = cmd;                        /* 偏移 4 */

    /* --- 载荷 --- */
    for (i = 0u; i < (size_t)payload_len; i++) {
        out[5u + i] = payload[i];        /* 偏移 5 开始 */
    }

    /* --- 校验：范围是 [0, 5+payload_len)，
     * 也就是把帧头、长度、序号、命令、载荷全都算进去。
     * 只算载荷的话，长度字段被干扰时校验还能通过，接收端就按错误的长度切帧。 --- */
    out[5u + (size_t)payload_len] = Protocol_Crc8(out, 5u + (size_t)payload_len);

    return total;
}
```

### 4.3 `protocol.c` 的核心：状态机解析

```c
ProtoStatus Protocol_ParserFeed(ProtoParser *p, uint8_t byte)
{
    if (p == NULL) { return PROTO_ERR_NULL; }

    switch (p->state) {

    /* ---------- 状态 1 / 2：找帧头 ---------- */
    case PROTO_ST_WAIT_SOF1:
    case PROTO_ST_WAIT_SOF2:
        if (byte == PROTO_SOF1) {
            /* 收到 0xA5 就认为"可能是帧头"，但要记住"可能"这两个字。
             * 真正确认帧头是在长度和 CRC 都过了之后 —— 这就是为什么
             * 载荷里出现 0xA5 0x5A 也不会把整帧解析坏，最多多走一遍状态机。 */
            p->state = PROTO_ST_WAIT_SOF2;
            return PROTO_OK;
        }
        if ((p->state == PROTO_ST_WAIT_SOF2) && (byte == PROTO_SOF2)) {
            /* 两个帧头字节都齐了，下一个字节就是长度字段 */
            p->state = PROTO_ST_READ_LEN;
            return PROTO_OK;
        }
        /* 既不是帧头第 1 字节、也不是在等第 2 字节时该来的 0x5A：
         * 丢掉这个字节，回到最初继续找。
         *
         * 说明：WAIT_SOF1 和 WAIT_SOF2 共用一个 case 标号，是为了让
         * "继续找帧头"这段逻辑只写一份。代价是这里三次 return 必须写全 ——
         * 只要漏掉一个，状态机就会永远停在 WAIT_SOF2 再也出不去，
         * 表现是"一帧都收不出来"（我第一次写就漏了去 READ_LEN 的那个分支，
         * 详见第 6 节的坑 6）。 */
        p->state = PROTO_ST_WAIT_SOF1;
        return PROTO_OK;

    /* ---------- 状态 3：读长度 ---------- */
    case PROTO_ST_READ_LEN:
        if (byte > (uint8_t)PROTO_MAX_PAYLOAD) {
            /* 长度不合理，说明这个 0xA5 0x5A 是载荷里的巧合。
             * 关键细节：如果刚收到的这个字节本身就是 0xA5，它有可能才是真帧头的
             * 第一个字节（载荷里出现 ... A5 5A A5 5A ... 这种情况），
             * 所以要回到 WAIT_SOF2 而不是 WAIT_SOF1，避免漏掉一帧。 */
            p->state = (byte == PROTO_SOF1) ? PROTO_ST_WAIT_SOF2 : PROTO_ST_WAIT_SOF1;
            return PROTO_ERR_TOO_LONG;
        }
        p->len   = byte;
        p->index = 0u;
        p->need  = (uint8_t)(byte + 2u);   /* 序号(1) + 命令(1) + 载荷(N) */
        p->state = (p->need == 0u) ? PROTO_ST_VERIFY : PROTO_ST_READ_BODY;
        return PROTO_OK;

    /* ---------- 状态 4：收序号 + 命令 + 载荷 ---------- */
    case PROTO_ST_READ_BODY:
        p->buf[p->index] = byte;
        p->index++;
        if (p->index >= p->need) {
            p->seq   = p->buf[0];
            p->cmd   = p->buf[1];
            p->state = PROTO_ST_VERIFY;
        }
        return PROTO_OK;

    /* ---------- 状态 5：核对校验 ---------- */
    case PROTO_ST_VERIFY: {
        uint8_t head[3];
        uint8_t calc;

        /* 校验范围要和发送端完全一致：[帧头(2) + 长度(1) + 序号(1) + 命令(1) + 载荷(N)]。
         * 这 5+N 个字节在解析器里不连续（帧头是常量、长度单独存、其余在 buf 里），
         * 所以分两段算：先算帧头 3 个字节，再用中间结果继续算 buf 里的 2+N 个字节。 */
        head[0] = PROTO_SOF1;
        head[1] = PROTO_SOF2;
        head[2] = p->len;

        calc = Protocol_Crc8(&head[0], 3u);
        calc = Protocol_Crc8Continue(calc, &p->buf[0], (size_t)p->need);

        if (calc == byte) {
            p->frame_count++;
            if (p->on_frame != NULL) {
                /* 载荷从 buf[2] 开始：buf[0] 是序号，buf[1] 是命令 */
                p->on_frame(p->cmd, p->seq, &p->buf[2], p->len);
            }
            p->state = PROTO_ST_WAIT_SOF1;
            return PROTO_FRAME_READY;
        }

        /* 校验失败：整帧丢弃，回到找帧头状态 */
        p->crc_error_count++;
        p->state = PROTO_ST_WAIT_SOF1;
        return PROTO_ERR_CRC;
    }

    default:
        p->state = PROTO_ST_WAIT_SOF1;
        return PROTO_ERR_NULL;
    }
}
```

### 4.4 STM32 侧：环形缓冲 + 中断 + 主循环（HAL 写法）

这一段是**我按 CubeMX 生成工程的 `USER CODE` 结构写的**，
🔬 还没有烧到板子上跑过（板子和 USB-TTL 还在路上），下面的代码是设计稿 + 预期行为。

```c
/* ---------------- 环形缓冲区（256 字节，2 的幂好取模） ---------------- */
#define RING_SIZE  256u

typedef struct {
    volatile uint8_t  buf[RING_SIZE];
    volatile uint16_t head;    /* 只在中断里动 */
    volatile uint16_t tail;    /* 只在主循环里动 */
} RingBuf;

static RingBuf      g_rx_ring;
static ProtoParser  g_parser;

/* 中断里调用：塞一个字节 */
static inline void RingBuf_Push(RingBuf *r, uint8_t b)
{
    uint16_t next = (uint16_t)((r->head + 1u) % RING_SIZE);
    if (next == r->tail) {
        return;                /* 满了：丢掉这一个字节，不覆盖老数据。
                                * 覆盖老数据会让状态机收到顺序错乱的字节，直接解析崩掉 */
    }
    r->buf[r->head] = b;
    r->head = next;
}

/* 主循环里调用：取一个字节，队列空返回 0 */
static inline int RingBuf_Pop(RingBuf *r, uint8_t *out)
{
    if (r->head == r->tail) {
        return 0;
    }
    *out = r->buf[r->tail];
    r->tail = (uint16_t)((r->tail + 1u) % RING_SIZE);
    return 1;
}

/* ---------------- 接收中断：只做"取字节 + 存字节" ---------------- */
void USART1_IRQHandler(void)
{
    /* 读 SR 判断 RXNE（读数据寄存器非空）。
     * HAL 里用 __HAL_UART_GET_FLAG()，这里用寄存器写法是为了说明它到底做了什么：
     * 读一次 DR 就自动把 RXNE 清掉了。 */
    if (USART1->SR & USART_SR_RXNE) {
        uint8_t b = (uint8_t)(USART1->DR & 0xFFu);
        RingBuf_Push(&g_rx_ring, b);
        /* 绝对不要在这里解析、更不要 printf —— 见第 6 节的坑 4 */
    }
}

/* ---------------- 解析回调：一帧解出来之后 ---------------- */
static volatile int16_t g_setpoint, g_actual, g_output;

static void OnFrame(uint8_t cmd, uint8_t seq, const uint8_t *payload, uint8_t len)
{
    (void)seq;
    if ((cmd == PROTO_CMD_PID_DATA) && (len == 6u)) {
        /* 小端拼 int16：低字节在前。
         * 这里手写而不是强转指针，是为了不依赖对齐 —— 载荷缓冲区不保证 2 字节对齐。 */
        g_setpoint = (int16_t)((uint16_t)payload[0] | ((uint16_t)payload[1] << 8));
        g_actual   = (int16_t)((uint16_t)payload[2] | ((uint16_t)payload[3] << 8));
        g_output   = (int16_t)((uint16_t)payload[4] | ((uint16_t)payload[5] << 8));
    }
}

/* ---------------- 发送：每 10 个控制周期发一帧（100 Hz 降采样） ---------------- */
static uint32_t g_tick = 0u;
static uint8_t  g_tx_seq = 0u;

static void ReportPid(void)
{
    uint8_t buf[PROTO_MAX_FRAME];
    uint8_t payload[6];
    size_t  n;

    /* 打包：先手动把三个 int16 按小端铺进载荷 */
    payload[0] = (uint8_t)((uint16_t)g_setpoint & 0xFFu);
    payload[1] = (uint8_t)(((uint16_t)g_setpoint >> 8) & 0xFFu);
    payload[2] = (uint8_t)((uint16_t)g_actual   & 0xFFu);
    payload[3] = (uint8_t)(((uint16_t)g_actual   >> 8) & 0xFFu);
    payload[4] = (uint8_t)((uint16_t)g_output   & 0xFFu);
    payload[5] = (uint8_t)(((uint16_t)g_output   >> 8) & 0xFFu);

    n = Protocol_Pack(buf, sizeof(buf), PROTO_CMD_PID_DATA, g_tx_seq, payload, 6u);
    if (n > 0u) {
        (void)HAL_UART_Transmit(&huart1, buf, (uint16_t)n, 10u);  /* 超时 10 ms */
        g_tx_seq++;                       /* 序号自增，上位机靠它算丢帧率 */
    }
}

/* ---------------- 主循环（CubeMX 的 while (1) 里） ---------------- */
/* USER CODE BEGIN WHILE */
Protocol_Init(&g_parser, OnFrame);

while (1)
{
    uint8_t b;

    /* 1) 把环形缓冲里的字节全部喂给状态机 */
    while (RingBuf_Pop(&g_rx_ring, &b)) {
        (void)Protocol_ParserFeed(&g_parser, b);   /* 半包/粘包都由状态机自己处理 */
    }

    /* 2) 每 10 个 1 kHz 周期上传一帧（100 Hz），给控制循环留余量 */
    if (g_tick % 10u == 0u) {
        ReportPid();
    }
    g_tick++;

    /* 3) 板载 OLED 上顺手显示一帧，不接上位机也能看个大概 */
    /* OLED_ShowNum(0, 0, (uint32_t)g_actual, 5, 12); */
}
/* USER CODE END WHILE */
```

|---|---|---|

| 波特率 | 115200 | 8 位数据、无校验、1 位停止（8N1） |

## 5. 逐段解释

**`PROTO_OVERHEAD = 6` 是怎么算出来的。**
2（帧头）+ 1（长度）+ 1（序号）+ 1（命令）+ 1（校验）= 6。
这个宏在代码里到处用（算总长度、算 CRC 覆盖范围、判断缓冲区够不够），
如果哪次改帧格式漏改了某一处，就会出一个很难查的 bug，所以我把所有
"6"都换成了这个宏，代码里不出现裸数字。

**`Protocol_Crc8()` 和 `Protocol_Crc8Continue()` 为什么要分成两个函数。**
解析器要校验的字节在内存里是**不连续**的：帧头两个字节是编译期常量（在 `.rodata` 段），
`LEN` 单独存在 `p->len` 里，`SEQ/CMD/载荷` 在 `p->buf` 里。
想用一次 `Protocol_Crc8(ptr, len)` 算完，就得先把它们 `memcpy` 拼成一个临时数组——
多一次拷贝、多一段栈空间，还容易写错长度。
CRC 的好处是**可以增量计算**（先算前 3 个字节拿到中间结果，再拿这个结果继续算后面的），
所以拆成两个函数之后，一行 `memcpy` 都不用。
这也是我在自测程序里专门加了"分段续算 == 整体计算"这条断言的原因。

**`Protocol_Crc8Continue` 里 `if (data == NULL) return crc;` 这一句。**
正常的 CRC 实现里很少有这个判断。我加它是因为：如果写成 `return 0x00u`，
那么"传了空指针"就会**静默地把校验结果清零**，接着 CRC 比较失败、
帧被丢掉，而你看不到任何报错。返回原值则是"什么都没发生"，
语义上更合理，也不会掩盖错误。

**`out[2] = payload_len;` 这一句为什么不用 `htons()` 之类的转换。**
因为 `LEN` 只有 1 个字节。单字节的数据没有"字节序"的概念——
在小端机器和大端机器上，`out[2]` 都是同一个值。
字节序只影响 2 字节及以上的整数（这就是为什么 `SEQ`、`CMD` 都只用 1 字节，
只有载荷里的 `int16` 才要显式按小端铺字节）。

**`need = byte + 2u` 里的 `+2` 是什么。**
状态机在 `READ_BODY` 阶段收的是"序号 + 命令 + 载荷"三段，
所以 `buf` 需要 `N + 2` 个字节，而不是 `N` 个。
`payload` 数据的起点因此是 `&p->buf[2]`。
如果写成 `need = byte`，那么载荷的最后一个字节就永远收不到，
每帧都会卡在 `READ_BODY` 直到下一个字节把它顶出去 —— 表现是"只能解出第一帧的第二帧开始全乱"。

**`p->index` 和 `p->need` 都用 `uint8_t`。**
因为最大载荷 32 字节 → `need` 最大 34，一个字节装得下。
用 16 位是浪费（在 8 位机上还要多做一次取低字节），用 `uint8_t` 正好，
但要注意 `byte + 2u` 的运算是在 `int` 里做的，赋回 `uint8_t` 时
已经判断过 `byte ≤ 32`，不会溢出。

**回调里为什么用 `memcpy` 抓数据（自测程序里）。**
回调拿到的 `payload` 指针指向的是**解析器内部的 `buf`**，
回调一返回，下一个字节就会往里写。
所以回调里必须"要么当场用完，要么拷走"，不能把这个指针存起来以后再读。

**`RingBuf_Push()` 里满了为什么是"丢掉新数据"而不是"覆盖老数据"。**
如果覆盖老数据，尾部就变成了一个新的字节 —— 状态机正在收的帧会从中间断掉，
它会用半截载荷去算 CRC，失败，然后重新找帧头。一次覆盖造成的是一帧的损失，
看起来更"经济"。
但问题是：**丢掉的这一帧里可能正好包含帧头**，那么后面的数据永远对不齐了。
丢新的字节则保证了"已经进入缓冲区的字节流是连续的、顺序正确的"，
状态机最多是少收一帧，不会错位。宁可丢帧，不可错位。

**`g_tick % 10u == 0u` 的降采样。**
PID 是 1 kHz 在跑，但上传只做 100 Hz。
理由在 2.9 节算过：1 kHz 上传时的 12 字节要占用约 1.0 ms，
而每个控制周期只有 1.0 ms，等于把串口发送塞满了整个周期。
调试看曲线，100~200 Hz 已经足够看清超调、震荡、稳态误差；
真想看高频细节，F103 的 USART1 还能跑 460800，那是另一条路。

**`HAL_UART_Transmit(..., 10u)` 的超时为什么是 10 ms。**
12 字节在 115200 下需要 `12 × 87 µs ≈ 1.04 ms`，10 ms 是 10 倍余量。
超时时间不能省 —— 如果 USB-TTL 拔了，`TXE` 标志永远不会置位，
没有超时的阻塞发送会**卡死在循环里**，整个机器人失控。

**`(void)Protocol_ParserFeed(...)` 前面为什么要加 `(void)`。**
`Protocol_ParserFeed` 的返回值是有意义的（能告诉你刚刚是不是收到了一帧、或者 CRC 错了）。
在"把环形缓冲里所有字节倒进去"这个循环里我不关心返回值，所以显式写上 `(void)`
告诉编译器和读代码的人"这是故意的，不是忘了检查"。
在真正需要的地方（比如统计 CRC 错误率）我会去检查它。

## 6. 我踩的坑

### 坑 1：结构体没加 `packed`，`memcpy` 发出去的数据上位机解开全是错的

**做法**：我把 PID 的数据定义成一个结构体，然后整块发出去：

```c
typedef struct {
    uint8_t  seq;         /* 我以为是偏移 0 */
    uint32_t timestamp;   /* 我以为是偏移 1 */
    int16_t  value[3];    /* 我以为是偏移 5 */
} MyPidData;

MyPidData d;
memcpy(txbuf, &d, sizeof(d));
HAL_UART_Transmit(&huart1, txbuf, sizeof(d), 100);
```

**现象**：上位机按 `seq / timestamp / value[3]` 解包，
`timestamp` 解出来是 `0x0000D007` 这种天文数字，`value` 全是垃圾。
但 `seq` 永远是对的 —— 因为它在偏移 0，无论怎么对齐都在第一个字节。

**定位过程**：我用串口助手把原始字节抓出来看，
发现第一个字节对，第二个字节开始就什么都对不上。
然后我把 `sizeof(MyPidData)` 打印出来：**是 12 字节，不是我以为的 11 字节**
（1 + 4 + 6 = 11）。

编译器为了把 `uint32_t timestamp` 对齐到 4 的倍数，
在 `seq`（偏移 0）后面塞了 **3 个填充字节**，所以 `timestamp` 实际在偏移 4，
`value` 实际在偏移 8，总共 12 字节。

```text
我以为的：  seq | timestamp(4)       | value[3](6)              = 11 字节
实际的：    seq | 填充(3) | timestamp(4) | value[3](6)          = 12 字节
            0     1 2 3    4 5 6 7        8 ... 13
```

**是我的问题**：我把"C 结构体内存布局"当成了"字段按顺序紧挨着排"。
C 标准只保证成员的**顺序**，不保证没有填充。

**怎么修的**：放弃"结构体直接 `memcpy` 发送"这个思路，
改成在 `Protocol_Pack()` 里按字节偏移一个一个往 `out[]` 里写。
理由在 2.6 节说过：`packed` 能解决 `sizeof`，但会引出"未对齐访问"的新问题
（在 Cortex-M0 上直接硬件异常），而且 `packed` 不是 C 标准。

**留下的防线**：`code/protocol/test_protocol.c` 的第 9 组用例把
`sizeof()` 和 `offsetof()` 打印出来并断言，以后改结构体定义时会被测试拦住。

### 坑 2：帧头只用单字节 `0xAA`，载荷里一出现它就误同步

**做法**：第一版帧头我用了很经典的 `0xAA`（一个字节）。

**现象**：数据流里偶尔冒出一帧，载荷内容是别的帧的尾巴；有时候连续几帧都解析不出来。
`crc_error_count` 一直在涨。

**定位过程**：我在解析器里加了一行调试输出，把每次"进入 VERIFY 状态"时
的 `p->len` 打出来，发现**长度字段是随机值**（比如 0x9C、0x5F）。
正常帧的 `LEN` 只应该是 6（PID 数据）。这说明状态机认了一个**假的帧头** ——
`0xAA` 出现在载荷中间，后面跟着的字节被当成了 `LEN`。

算了一下概率：载荷里的字节如果是均匀的，撞上 `0xAA` 的概率是 1/256。
一帧 6 字节载荷、1000 帧/秒 → 每秒约 23 次误同步。这个频率和现象完全对得上。

**怎么修的**：两处一起改。
(1) 帧头改成两个字节 `0xA5 0x5A`，概率降到 1/65536；
(2) `READ_LEN` 里加了"`LEN > 32` 就判为假帧头"的判断，
让绝大多数的误同步在读到长度时就退出来，不用等 CRC。
改完之后，我专门写了第 6 组测试用例（载荷里故意塞 `0xA5 0x5A`）来锁住这个行为。

**剩下的残余风险我也记一下**：如果载荷里出现 `A5 5A 06 ...`（长度字段也正好合法），
状态机会一路走到 `VERIFY` 才靠 CRC 把它拦下来。
所以**帧头负责降低误同步概率，CRC 负责兜底**，两者缺一不可——这也是我不接受"反正有 CRC 就不用管帧头"这个说法的原因。

### 坑 3：校验和没算长度字段，长度被干扰时校验照样通过

**做法**：第一版的 CRC 我只对**载荷**计算：

```c
/* 错误写法：只校验载荷 */
out[5 + payload_len] = Protocol_Crc8(payload, payload_len);
```

**现象**：用一个故意改坏的帧做实验：把 `LEN` 从 `0x06` 改成 `0x07`、其余不动，
接收端居然**接受了这一帧**（CRC 通过），然后因为长度是 7，
它把下一帧的第一个字节也吃进了载荷，后面整条流全部错位。

**定位过程**：其实不用定位——我在写"CRC 到底该覆盖哪些字节"这一段时，
用自测程序写了这条断言：

```c
/* 校验范围必须包含 LEN 字段：把长度改一位，CRC 就应该跟着变 */
frame[2] = 7u;
CHECK(Protocol_Crc8(frame, 11u) != frame[11]);
```

第一次跑就 FAIL 了，因为我当时用的是旧公式。

**怎么修的**：把校验范围改成从**偏移 0 开始**、
覆盖 `2 + 1 + 1 + 1 + N = 5 + N` 个字节：

```c
out[5u + (size_t)payload_len] = Protocol_Crc8(out, 5u + (size_t)payload_len);
```

**这个坑背后的道理**：CRC 只能保护"参与计算的字节"。
帧头、长度、序号、命令这些"协议控制字段"如果不参与校验，
它们被干扰时接收端会毫无察觉 —— 而且危害比载荷出错更大，
因为载荷出错只影响一帧的数据，长度字段出错会让**后面所有的帧**都错位。

**顺带一个发现**：`SEQ` 参与 CRC 之后，"序号被干扰"会被当成 CRC 错误丢掉。
这是对的（数据确实不可信了），但要注意：
**如果你用 `SEQ` 算丢帧率，那么被 CRC 丢掉的帧也会体现为"序号跳变"**，
两者要在统计上分开看，别把 CRC 拦截的帧也算成"传输丢失"。

### 坑 4：在串口中断里直接跑解析和 printf，1 kHz 数据一来就丢包

**做法**：第一版我图省事，直接在 `HAL_UART_RxCpltCallback()` 里
把收到的字节喂给状态机，解析出数据后立刻 `printf` 一行调试信息。

```c
/* 错误写法：中断里干了太多事 */
void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)
{
    Protocol_ParserFeed(&g_parser, g_rx_byte);   /* 解析 */
    printf("rx ok\r\n");                          /* 打印！ */
    HAL_UART_Receive_IT(huart, &g_rx_byte, 1);
}
```

**现象**（🔬 这是预期现象，我还没上机；下面写的是这套写法**会**导致什么，
以及我改掉它的理由）：把发送频率提到 1 kHz 之后，
上位机上的曲线每隔一段就断一截，`crc_error_count` 涨得很快，
同时 PID 的输出波形出现周期性的抖动。

**原因分析**：`printf` 重定向到串口之后是**阻塞**的。
`"rx ok\r\n"` 是 7 个字符，在 115200 下要发 7 × 87 µs ≈ **0.6 ms**。
而串口一秒钟来 1000 × 12 = 12000 个字节，也就是**每 83 µs 就有一个新字节到达**。

```text
中断里花 0.6 ms 打印 → 这 0.6 ms 内到达的 7 个字节
                      → 接收寄存器 USART_DR 只能存 1 个
                      → 其余的触发 ORE（溢出错误）标志，字节直接丢
```

再加上解析 + CRC 的时间，中断一次要占掉 700 µs 左右，
而 1 kHz 的控制周期总共才 1000 µs —— **中断把 CPU 占满了，PID 计算被挤掉**，
这才是"输出波形周期性抖动"的根本原因。

**怎么修的**：按 2.7 节的分工重构：

| 位置 | 只做这些 |
|---|---|
| `USART1_IRQHandler` | 读 `DR` 拿 1 个字节 → `RingBuf_Push()` → 返回（几十个时钟周期） |
| 主循环 | `RingBuf_Pop()` 出队 → `Protocol_ParserFeed()` → 更新数据 |
| 主循环（降采样后） | 每 10 个周期打包一帧 `HAL_UART_Transmit()` 发出去 |

**教训**：中断服务函数的判断标准不是"这段代码能不能放进中断"，
而是"这段代码要花多少微秒，占中断源周期的百分之几"。
串口在 115200、1 kHz 数据率下，每 83 µs 就来一个字节，
中断里能用掉的时间上限就是几十微秒量级，任何"打印、等待、循环"都是禁区。

### 坑 5（不算坑，但值得记）：`LEN > 32` 的判断一开始写漏了

我最初的状态机里 `READ_LEN` 只做了 `p->len = byte;`，
没有检查长度是否越界。结果是：一个假帧头后面跟着一个 `LEN = 0xFF`（255），
解析器就往 `buf[34]` 里写 255 个字节 —— **直接写穿栈上/全局的相邻内存**。

这个 bug 在我加"载荷里塞假帧头"的测试用例时才暴露出来（第 6 组用例跑到一半程序崩了）。
修法是两条：

1. `READ_LEN` 里加 `if (byte > PROTO_MAX_PAYLOAD) { ... }` 的越界判断；
2. `buf` 的大小严格写死 `PROTO_MAX_PAYLOAD + 2`，并且用 `p->need` 做写入循环的上界，
   而不是用"收到的字节数"当上界。

**这条让我记住一件事**：解析外部输入（不管是串口、CAN 还是文件）的代码，
**每一个来自外部的长度字段在使用前都必须先做边界检查**。
后面我做上位机下发的 `SET_PARAM` 命令时，这条规则也一样适用 ——
上位机是可以被攻击者伪造的，长度字段不能信。

### 坑 6：`switch` 里两个状态共用一个 `case`，漏了一个分支，一帧都收不出来

这是我写这一章**真正花掉最多时间**的一个 bug，而且它就藏在我自己觉得"写得挺聪明"的那段代码里。

**做法**：我想让 `WAIT_SOF1` 和 `WAIT_SOF2` 共用一段"继续找帧头"的逻辑，
所以写成了两个 `case` 标号叠在一起：

```c
/* 错误写法 */
case PROTO_ST_WAIT_SOF1:
case PROTO_ST_WAIT_SOF2:
    if (byte == PROTO_SOF1) {
        p->state = PROTO_ST_WAIT_SOF2;      /* 收到 0xA5 */
    } else {
        p->state = PROTO_ST_WAIT_SOF1;      /* 不是 0xA5，重找 */
    }
    return PROTO_OK;                        /* ← 就是这里出的事 */
```

**现象**：自测程序里 42 项断言失败，所有需要解析帧的用例**全部**解不出帧
（`frame_count == 0`、`crc_error_count == 0`）。注意 `crc_error_count` 也是 0 ——
这个细节很关键：CRC 一次都没算过，说明状态机根本没走到 `VERIFY`。
只有第 1 组（CRC 本身）和第 9 组（结构体对齐）过了，因为它们不经过状态机。

**定位过程**：`crc_error_count == 0` 这一条把我从"CRC 算错了"这个方向拉了出来。
CRC 一次都没被调用，问题只能在状态机**没走到** `VERIFY`。
于是我回头逐字节推演：

```text
喂 A5 → WAIT_SOF1 收到 0xA5 → 进 WAIT_SOF2 ✔
喂 5A → 还是 WAIT_SOF2 → 判断 byte == 0xA5 吗？不是 → 回 WAIT_SOF1 ✘
        这一个字节的 0x5A 被吃掉了，状态反而退回去了
```

我看了一眼 `case` 标号就明白了：**两个状态共用一个 `case`，
但 `case` 标号本身不会"跳"**，C 的 `switch` 里同一个 `case` 体只会被执行一次，
不存在"先按 WAIT_SOF1 的逻辑走一遍、再按 WAIT_SOF2 的逻辑走第二遍"这件事。
想让"收到 `0x5A` 之后进入 `READ_LEN`"生效，必须在同一个 `case` 体里
**显式写一个分支**：

```c
/* 正确写法：三次 return 都要写全 */
case PROTO_ST_WAIT_SOF1:
case PROTO_ST_WAIT_SOF2:
    if (byte == PROTO_SOF1) {
        p->state = PROTO_ST_WAIT_SOF2;
        return PROTO_OK;                          /* ← 分支 1 */
    }
    if ((p->state == PROTO_ST_WAIT_SOF2) && (byte == PROTO_SOF2)) {
        p->state = PROTO_ST_READ_LEN;
        return PROTO_OK;                          /* ← 分支 2（原来漏的就是这个） */
    }
    p->state = PROTO_ST_WAIT_SOF1;
    return PROTO_OK;                              /* ← 分支 3 */
```

**为什么会漏**：我在脑子里把状态机"按状态"想了一遍，
觉得 `WAIT_SOF1: case WAIT_SOF2:` 这种写法就等于"这两个状态各自执行自己的逻辑"，
于是只写了"等到 0x5A 就往下走"的一半。
实际上 `case` 标号只是**跳转入口**，两个标号指的是**同一段代码** ——
它们之间没有隐式的"上一个状态走完了"这回事。

这里还有一个双重的教训：**如果用 `fallthrough` 的写法**（`WAIT_SOF2` 那个 `case`
不写 `return`，让控制流"掉进"`READ_LEN` 的 `case`），也能实现同样的效果：

```c
case PROTO_ST_WAIT_SOF2:
    if (byte != PROTO_SOF2) { p->state = PROTO_ST_WAIT_SOF1; return PROTO_OK; }
    /* fall through —— 故意不 break，掉进 READ_LEN */
case PROTO_ST_READ_LEN:
    ...
```

这种写法编译器会用一个 `-Wimplicit-fallthrough` 警告提醒我"你是不是忘了 `break`"，
反而是**更安全**的写法。但我在整理这一章的时候选了"三个 `return` 写全"的版本，
因为它不依赖"读者知道这里故意不写 `break`"，坏处就是刚才那个坑：
**共用 `case` 的代码里，每一条出口都必须自己写出来，漏一条就是一个死循环式的 bug。**

**教训**：写状态机的时候，**每个状态的每一条出口都要能一眼数出来**。
我后来给自己定的检查方法是：在纸上（或注释里）把"这个状态能收到的所有输入"列成一列，
把"每种输入去哪"填在右边，填不满就有漏。
像 `WAIT_SOF1` 的输入其实只有两类（是 `0xA5` / 不是 `0xA5`），
`WAIT_SOF2` 有三类（`0x5A` / `0xA5` / 其他），一共 5 条出口，
数一数代码里的 `return` 是不是 5 个 —— 我就是这么发现漏了一条的。

顺便说：这个 bug 也说明了**为什么自测程序要穷举所有切分点、要逐字节喂**。
如果我只测"整帧一次喂进去"，这个 bug 一样会暴露（因为每帧都过不了 `WAIT_SOF2`）；
但如果我只手工测了一次、看到"解不出来"就去怀疑 CRC，
那就会在错误的方向上改半天。

## 7. 复现步骤

### A. 先在 PC 上把协议逻辑跑通（不需要任何硬件）

1. 装一个 gcc。Windows 上装 MinGW-w64（或者用 MSYS2、WSL 里的 gcc），
   Linux/macOS 一般自带。验证：

   ```bash
   gcc --version
   ```

2. 进到代码目录：

   ```bash
   cd stm32-learning-notes/code/protocol
   ```

3. 编译（`-Wall -Wextra` 必须零警告）：

   ```bash
   gcc -O2 -std=c99 -Wall -Wextra -o test_protocol test_protocol.c protocol.c
   ```

4. 运行：

   ```bash
   ./test_protocol        # Windows 下是 .\test_protocol.exe
   ```

5. 看最后一行的 `结果:` 是不是 `ALL PASS`，程序返回码是不是 0：

   ```bash
   echo $?               # Windows PowerShell 里是 $LASTEXITCODE
   ```

6. 重点看第 4 组（半包）和第 5 组（粘包）的输出 —— 它们会打印
   "全部 N 个切分点都正确"，N 应该等于整帧长度减 1。

### B. 配置 STM32 工程

7. CubeMX 新建工程，选 `STM32F103C8Tx`。
8. `System Core → RCC`：`High Speed Clock (HSE)` 选 `Crystal/Ceramic Resonator`。
9. `Clock Configuration` 页：`HSE` 填 8，`PLL Mul` 选 `X9`，
   `System Clock Mux` 选 `PLLCLK`，确认 **HCLK = 72 MHz**。
10. `Connectivity → USART1`：`Mode` 选 `Asynchronous`。
    参数保持默认：`115200` `8` `N` `1`。
11. `NVIC Settings` 页（在 USART1 的配置里）：
    把 `USART1 global interrupt` 勾上 **Enabled**。
12. `Project Manager`：`Toolchain/IDE` 选 `MDK-ARM V5`，
    生成工程后用 Keil 打开。
13. 把 `protocol.h` 和 `protocol.c` 两个文件加进 Keil 工程
    （右键 `Source Group 1 → Add Existing Files`）。
    **不要**把 `test_protocol.c` 加进去（里面有自己的 `main()`，会和 CubeMX 生成的 `main()` 冲突）。
14. 在 `main.c` 的 `/* USER CODE BEGIN 0 */` 里贴 4.4 节的环形缓冲、
    中断处理和 `OnFrame()`；在 `/* USER CODE BEGIN WHILE */` 里贴主循环那段。
15. 编译，用 ST-Link 烧录。

### C. 连线

16. USB-TTL 的 **RXD** 接 STM32 的 **PA9（TX）**，
    USB-TTL 的 **TXD** 接 STM32 的 **PA10（RX）**，
    **GND 接 GND**（这一步最容易被忘，忘了就是满屏乱码或者什么都没有）。
17. USB-TTL 插到电脑，设备管理器里确认 COM 口号（比如 `COM3`）。

### D. 上位机看曲线

18. 装依赖：

    ```bash
    pip install pyserial matplotlib
    ```

19. 用 `code/protocol/README.md` 里那段 Python 先把数据打印出来
    （先把 `COM3` 改成你的口号），确认能打出 `seq / 目标 / 实际 / 输出` 四个数。
    这一步是**先证明通信打通**，别一上来就调绘图，不然出了问题分不清是通信还是绘图。
20. 数据能正常打印之后，再把 `print` 换成 matplotlib 或 pyqtgraph 的实时绘图。
21. 检查丢帧率：看 `seq` 是不是连续递增。断了几号就说明丢了几帧，
    把它除以总帧数就是丢帧率。🔬 目标是不超过 0.1%（这个目标值要上机实测后再定）。

## 8. 自测题（面试可能这么问）

**Q1：你的协议为什么不用 `printf` 发文本？文本不是更好调试吗？**

A：调试方便是文本唯一的优势，所以我在开发阶段确实会留一个
`PROTO_CMD_DEBUG_TEXT` 命令字走文本。但**控制数据**不能用文本，三个原因：

1. **变长**：`printf("%d", 5)` 是 1 个字符，`printf("%d", 12345)` 是 5 个字符，
   接收端没法靠固定长度切帧。
2. **解析慢**：上位机要做字符串到整数的转换（`sscanf`/`atoi`），
   比直接按字节拼整数慢一个量级。
3. **最关键的是时间**：`printf` 是阻塞发送，在 115200 下发一帧 11 字节要
   约 0.96 ms，而我的控制周期只有 1 ms —— 光打印就把周期占满了。

具体的带宽和周期账在 2.1 节算过。

**Q2：帧头为什么用两个字节？为什么不用 `0x00` 或 `0xFF`？**

A：单字节帧头在随机载荷里撞上的概率是 1/256。以 1 kHz、每帧 6 字节载荷算，
每秒约 23 次误同步，每次都会冲掉真正的帧边界。
两个字节把概率降到 1/65536（每秒约 0.09 次），而且每次都能被 CRC 拦下。

不用 `0x00`/`0xFF` 是因为这两个值在**故障状态**下会大量出现：
线路断开或浮空时读到的常是 `0xFF`，缓冲区清零后是 `0x00`。
用它们当帧头，会把"线断了"误判成"帧头来了"。
`0xA5 0x5A` 二进制是 `10100101` / `01011010`，互补且位模式交替均匀，
在连续 0、连续 1、递增序列里都不容易出现。

**Q3：你的状态机是怎么处理"一帧收了一半"和"两帧粘在一起"的？**

A：因为它是**逐字节**推进的，不是"等一帧收完再解析"。

- 半包：收到第 6 个字节时状态停在 `READ_BODY`、`index = 1`，静静等下一个字节。
  半包对它来说就是正常情形，没有任何特殊分支。
- 粘包：第 1 帧 `VERIFY` 通过、回调之后状态被置回 `WAIT_SOF1`，
  下一个字节如果是 `0xA5` 就开始解析第 2 帧。
  同样没有特殊分支。

我的自测程序第 4 组用例是**穷举整帧的所有切分点**（从第 1 个字节后切开一直
到倒数第 2 个字节后切开），第 5 组测粘包 —— 这两种错误靠手动测试覆盖不全，
必须写成自动化用例。

**Q4：CRC 的校验范围包括哪些字节？如果只校验载荷会怎样？**

A：包括从偏移 0 开始的 `5 + N` 个字节：帧头（2）+ 长度（1）+ 序号（1）+ 命令（1）+ 载荷（N）。

只校验载荷的话，**长度字段被干扰时 CRC 照样通过**。
接收端就按错误的长度去切帧，把下一帧的字节当成自己的载荷尾巴 ——
错的不是一帧，是**后面所有的帧**。
同理，帧头、序号、命令字段被干扰也不会被发现。
所以协议控制字段必须一起参与校验。

**Q5：STM32 是小端，PC 也是小端，那 `int16` 直接发过去不就行了，为什么还要关心字节序？**

A：在"两边都是小端"的前提下确实能用，但这是**依赖平台的巧合**：

1. 上位机如果用 Python 的 `struct.unpack`，不显式写 `<` 就会用本机字节序，
   换一台大端机器（或者某些 ARM 服务器）就解错。
   写 `<` 是零成本的。
2. 更实际的风险是**对齐**，不是字节序。结构体默认对齐会插入填充字节，
   `struct { uint8_t a; uint32_t b; }` 占 8 字节而不是 5 字节，
   `memcpy` 整块发出去接收端从第 2 个字段起全错位。
   我的做法是按字节偏移手写打包，不依赖结构体内存布局。
3. `memcpy` 一整块还有个隐患：`uint32_t` 成员如果地址不是 4 的倍数，
   在 Cortex-M0 上会直接触发硬件异常。F103（M3）支持非对齐访问所以看不出来，
   换个芯片就炸。手写字节偏移没有这个问题。

**Q6（加分）：`RingBuf` 满了你丢新数据还是覆盖老数据？为什么？**

A：丢新数据。覆盖老数据会破坏"缓冲区里的字节流是连续的、顺序正确的"这个前提 ——
状态机可能正在收一帧的中间，尾部被换成新字节之后，它会拿半截载荷算 CRC、
失败、重找帧头。更糟的情况是被覆盖掉的字节里正好有帧头，之后整条流永远对不齐。

丢新数据至少保证"已经进来的数据是完整的"。代价是丢一帧，收益是不会错位。
**宁可丢帧，不可错位。**

**Q7（加分）：你的协议能不能直接用在 RM 电机通信上？**

A：不能直接用（电机是 CAN，报文格式由电调固件规定，我不能改），
但**这一章练的能力可以直接迁移**：定长字段按偏移读写、小端拼 `int16`、
减速比换算、长度/边界检查。
差别在于 CAN 的报文最长 8 字节，而且 CAN 硬件层自带 CRC 和自动重发，
所以不需要我再放校验字段 —— 这也说明"要不要校验"取决于下层提供了什么，
不是无条件的教条。
