## 1. 先想清楚一个问题：为什么「环境」值得单独写一章？

我原本以为环境搭建是最没技术含量的部分——装软件、点下一步，能有什么好讲的？

后来看到一个很具体的问题描述：**第一次烧录成功，第二次再也连不上芯片了。**

我顺着这个问题往下查，才明白它不是「运气不好」，而是一个可以解释清楚的现象：STM32 的下载调试口（SWD）用的是 PA13 和 PA14 两个**普通引脚**，它们复位后默认被调试外设占用。如果我在 CubeMX 里没有告诉它「这两个脚我要留着调程序」，生成的代码就可能把它们配成普通输出——程序一烧进去、芯片一复位，调试口就没了，而我又只能靠调试口才能改程序。**自己把自己锁在门外**，这就是那个现象的机制。

这件事让我改了看法。环境这一章真正要弄明白的不是「点哪个按钮」，而是这条链路上每一环负责什么：

```text
我写的 C 代码  →  编译器  →  一个能被芯片读的二进制文件
                                        │
                                   下载器（ST-Link）
                                        │  通过 SWD 两线
                                        ▼
                              芯片 Flash → 复位 → 取指 → 执行
                                        │
                          时钟没配好？GPIO 时钟没使能？引脚被复用？
                                        ▼
                                     LED 亮 / 不亮
```

出问题的时候，我要能判断它断在**哪一环**，而不是把「LED 不亮」当成一个整体去猜。这一章的每一节都是围绕这件事写的。

## 2. 原理：它到底是怎么工作的

### 2.1 四样工具各管什么

新手最容易犯的错，是分不清「哪个软件管哪一段」。我先把分工列清楚，后面出错时直接对号入座：

| 工具 | 它管什么 | 它**不**管什么 | 出错时的典型症状 |
|---|---|---|---|
| STM32CubeMX 6.x | 用图形界面选芯片、配引脚、配时钟树、生成工程骨架代码（HAL 库 + `main.c` + `.ioc`） | 不编译、不下载。它只**生成代码** | 生成的工程打不开、缺少 `Core/` 目录、芯片选错导致引脚全变 |
| Keil MDK-ARM 5.x | 编译、链接、把 `.axf/.hex` 通过 ST-Link 写进芯片；断点调试 | 不配对芯片外设（时钟、引脚是 CubeMX 的事） | 报红字 Build 失败；缺头文件；编译器版本不对 |
| ST-Link V2 + 驱动（STSW-LINK009） | 把电脑的 USB 转成芯片能懂的 SWD 时序；供电（可选） | 不参与代码内容 | 设备管理器里有黄色感叹号；Keil 报 "No target connected" |
| 串口助手（SSCOM / XCOM / VS Code Serial Monitor） | 显示芯片通过串口发出来的字符；也可发指令给芯片 | 不经 SWD，走的是 USART1 的 PA9/PA10 | 全是乱码；一个字都没有；能收不能发 |

一句话记住：**CubeMX 管「配什么」，Keil 管「编什么、烧进去」，ST-Link 管「怎么进去」，串口助手管「里面发生了什么」。**

### 2.2 时钟树：72 MHz 是怎么来的

这是本章最需要算清楚的东西。F103 芯片自己只有一个内部的 8 MHz RC 振荡器（HSI），精度差（数据手册给的 HSI 精度是 ±1% 量级，随温度漂移），量串口波特率容易出偏差；所以用板上那颗 8 MHz 石英晶振（HSE）做基准，再用 PLL 倍频上去：

```text
   HSE 晶振 8 MHz（接在 PD0-OSC_IN / PD1-OSC_OUT 上）
        │
        │  HSE 预分频 = /1        → 8 MHz（RCC_CFGR 的 PLLXTPRE 位）
        │  PLL 倍频 ×9            → 8 MHz × 9 = 72 MHz（RCC_CFGR 的 PLLMUL 位）
        ▼
   PLL 输出 72 MHz
        │  SYSCLK 源选 PLL        （RCC_CFGR 的 SW 位）
        ▼
   SYSCLK = 72 MHz
        │  AHB 预分频 /1
        ▼
   HCLK = 72 MHz ──┬── 内核、SRAM、Flash 接口、DMA
                   │
                   ├── APB1 预分频 /2 ──► PCLK1 = 36 MHz  ← APB1 的上限就是 36 MHz
                   │        └── 定时器时钟 ×2 → TIM2/TIM3/TIM4 = 72 MHz
                   │
                   └── APB2 预分频 /1 ──► PCLK2 = 72 MHz  ← APB2 可以跑到 72 MHz
                            └── 预分频为 /1，所以不倍频：TIM1 时钟 = 72 MHz
```

这里有三个容易记错的点，我单独列出来：

1. **APB1 必须分频**。APB1 上挂着 TIM2/3/4、USART2/3、I2C1/2、SPI2 这些外设，它的最高时钟是 **36 MHz**。72 MHz 直接给 APB1 就是超频，外设不会报错，只会**时序不准**——比如串口波特率对不上、I2C 时序超规。所以要 /2。
2. **定时器时钟会被硬件自动 ×2**。这个 ×2 只在 APB 预分频不等于 1 时生效。APB1 = 36 MHz，但 TIM2 拿到的是 **72 MHz**。第 4 章算 PWM 频率时用 `72 MHz / (psc+1) / (arr+1)`，用的就是这个 72 MHz，不是 36 MHz。
3. **72 MHz 下 Flash 要等**。Flash 的读取速度跟不上 72 MHz 的内核，必须插入等待周期。规则是：`0 < HCLK ≤ 24 MHz` 用 0 个等待周期，`24 < HCLK ≤ 48 MHz` 用 1 个，`48 < HCLK ≤ 72 MHz` 用 **2 个**。这就是 CubeMX 最后生成 `HAL_RCC_ClockConfig(&RCC_ClkInitStruct, FLASH_LATENCY_2)` 那个 `2` 的来历。写少了会取指出错，写多了只是慢一点。

### 2.3 SWD 和 JTAG：为什么选 SWD

芯片的调试口叫 SWJ（Serial Wire and JTAG），它有两种工作模式，共用同一批引脚：

| | JTAG | SWD（Serial Wire Debug） |
|---|---|---|
| 用几根线 | 5 根：TCK、TMS、TDI、TDO、nTRST | 2 根：SWCLK、SWDIO（还可选 1 根 SWO 做 trace） |
| 占用的引脚 | PA13、PA14、PA15、PB3、PB4 | PA13（SWDIO）、PA14（SWCLK） |
| 释放出的引脚 | 无 | PA15、PB3、PB4 可当普通 IO 用 |
| 调试能力 | 可接多器件菊花链 | 单器件，够日常用；SWO 能输出 trace/`printf` |
| 我的选择 | — | ✅ 选它 |

选 SWD 的理由就三条：**线少**（接线错的机会少）、**占引脚少**（PA15/PB3/PB4 能省下来）、**够用**（我不需要多器件菊花链）。

而「选 SWD」在 CubeMX 里对应的操作就是 **SYS → Debug → Serial Wire**。它生成的效果是在 `Core/Src/stm32f1xx_hal_msp.c` 的 `HAL_MspInit()` 里出现一句：

```c
__HAL_AFIO_REMAP_SWJ_NOJTAG();   /* JTAG-DP Disabled and SW-DP Enabled */
```

这句话的作用是往 AFIO 的 `AFIO_MAPR` 寄存器里写 SWJ_CFG = 010，意思是「关掉 JTAG，保留 SWD」。**PA13/PA14 保住了，PA15/PB3/PB4 空出来了。** 反过来，如果这一项没设对，PA13/PA14 就没有被保留，一旦被当成普通 IO 用，烧录后调试口就消失——这就是第 1 节说的「把自己锁在门外」，第 6 节有详细的排查和解法。

### 2.4 从 USB 到串口助手：为什么线是交叉的

串口助手和芯片之间还有一颗 **USB 转 TTL 芯片**（常见的是 CH340，也有 CP2102、FT232）。它们的 TX/RX 是**设备对设备**的关系，所以必须交叉：

```text
  电脑 USB ── USB-TTL 模块 ──┬── 模块 TX  ──►  板子 PA10 (USART1_RX)
                             ├── 模块 RX  ◄──  板子 PA9  (USART1_TX)
                             └── GND     ────  板子 GND   ← 一定要接，否则电平没有参考点，收不到
```

两个必须注意的地方：

- **电平必须是 3.3 V**。市面上有些模块是 RS-232 电平（±12 V 左右），直接接到 PA9 上会把引脚打坏。买的时候认准「3.3 V TTL」。
- 串口参数是 **115200 8N1**（波特率 115200 bit/s、8 个数据位、无校验、1 个停止位），两边必须完全一致，差一位就是乱码。

### 2.5 板载 LED 为什么是低电平点亮

Blue Pill 上的板载 LED 不在「输出高就亮」的那一侧：LED 的阳极通过一颗限流电阻接到 3.3 V，阴极接到 PC13。所以 PC13 输出**低电平**时回路才通、灯才亮；输出高电平时两端都是 3.3 V，没有压差，灯灭。

另外 PC13 这颗脚比较特殊。数据手册在引脚表的脚注里专门写了：PC13、PC14、PC15 由电源开关供电，**只能承受 3 mA 量级的电流，输出频率不能超过 2 MHz**。这也是为什么 CubeMX 给 PC13 生成的 `GPIO_SPEED_FREQ_LOW`（对应 2 MHz）是合适的——不是随便选的。想驱动大电流的东西（蜂鸣器、继电器、外接 LED 多颗），要另加三极管或驱动芯片，不能指望这个脚。

外部 LED 就正常多了，但**必须串限流电阻**。以 PA5 为例，PA5 输出 3.3 V，红色 LED 的正向压降约 2.0 V，取 330 Ω：

```text
I = (3.3 V − 2.0 V) / 330 Ω ≈ 3.9 mA
```

3.9 mA 足够看清亮灭，也远小于引脚的上限。如果换成 1 kΩ，电流只有 `(3.3 V − 2.0 V) / 1000 Ω = 1.3 mA`，能看见但偏暗；如果不串电阻，电流就只由引脚内阻和 LED 的动态电阻决定，完全不受控——这就是第 03 章要算的东西，这里只留结论。

## 4. 完整代码

这是 CubeMX 生成 + 我改了 3 行的第一个工程。**标 `[生成]` 的是 CubeMX 写的，标 `[我写的]` 的是我在 `USER CODE` 区里加的。** 我一个字都没有改生成的部分。

工程用的是 HAL 库，裸机，系统时钟 72 MHz，只用了 GPIOC 的 PC13（板载 LED）。

```c
/* Core/Src/main.c
 * 工程：code/00-blink
 * 芯片：STM32F103C8Tx   时钟：HSE 8 MHz × PLL9 = SYSCLK 72 MHz
 */
#include "main.h"

void SystemClock_Config(void);
static void MX_GPIO_Init(void);

int main(void)
{
  /* [生成] 复位所有外设、初始化 Flash 接口，并把 SysTick 配成 1 ms 中断 */
  HAL_Init();

  /* [生成] HSE 8 MHz → PLL ×9 → SYSCLK 72 MHz，APB1 /2 = 36 MHz，APB2 /1 = 72 MHz */
  SystemClock_Config();

  /* [生成] 使能 GPIOC 时钟，把 PC13 配成推挽输出 */
  MX_GPIO_Init();

  /* [生成] 主循环的骨架和它的保护标记都是 CubeMX 写的 */
  /* USER CODE BEGIN WHILE */
  while (1)
  {
    /* USER CODE END WHILE */

    /* USER CODE BEGIN 3 */
    /* ↓ 以下两行是我加的（[我写的]），它们必须在 BEGIN 3 和 END 3 之间 ↓ */
    HAL_GPIO_TogglePin(GPIOC, GPIO_PIN_13);  /* 翻转 PC13：板载 LED 亮 → 灭 → 亮 */
    HAL_Delay(500);                          /* 阻塞延时 500 ms，靠 SysTick 的 1 ms 中断计数 */
  }
  /* USER CODE END 3 */
}

/* ===== 以下两个函数全部由 CubeMX 生成，我一个字都没改 ===== */

/**
  * @brief  System Clock Configuration
  *         8 MHz HSE → PLL ×9 → 72 MHz SYSCLK
  */
void SystemClock_Config(void)
{
  RCC_OscInitTypeDef RCC_OscInitStruct = {0};
  RCC_ClkInitTypeDef RCC_ClkInitStruct = {0};

  /* HSE 打开、不分频，PLL 源选 HSE，倍频 9 倍：8 MHz × 9 = 72 MHz */
  RCC_OscInitStruct.OscillatorType      = RCC_OSCILLATORTYPE_HSE;
  RCC_OscInitStruct.HSEState            = RCC_HSE_ON;
  RCC_OscInitStruct.HSEPredivValue      = RCC_HSE_PREDIV_DIV1;  /* HSE 不分频 */
  RCC_OscInitStruct.HSIState            = RCC_HSI_ON;
  RCC_OscInitStruct.PLL.PLLState        = RCC_PLL_ON;
  RCC_OscInitStruct.PLL.PLLSource       = RCC_PLLSOURCE_HSE;
  RCC_OscInitStruct.PLL.PLLMUL          = RCC_PLL_MUL9;
  if (HAL_RCC_OscConfig(&RCC_OscInitStruct) != HAL_OK)
  {
    Error_Handler();
  }

  /* HCLK = 72 MHz（AHB /1），PCLK1 = 36 MHz（APB1 /2），PCLK2 = 72 MHz（APB2 /1） */
  RCC_ClkInitStruct.ClockType      = RCC_CLOCKTYPE_HCLK   | RCC_CLOCKTYPE_SYSCLK
                                   | RCC_CLOCKTYPE_PCLK1  | RCC_CLOCKTYPE_PCLK2;
  RCC_ClkInitStruct.SYSCLKSource   = RCC_SYSCLKSOURCE_PLLCLK;
  RCC_ClkInitStruct.AHBCLKDivider  = RCC_SYSCLK_DIV1;
  RCC_ClkInitStruct.APB1CLKDivider = RCC_HCLK_DIV2;
  RCC_ClkInitStruct.APB2CLKDivider = RCC_HCLK_DIV1;

  /* 第二个参数是 Flash 等待周期：48 MHz < HCLK ≤ 72 MHz 必须用 2 */
  if (HAL_RCC_ClockConfig(&RCC_ClkInitStruct, FLASH_LATENCY_2) != HAL_OK)
  {
    Error_Handler();
  }
}

/**
  * @brief  GPIO 初始化：PC13 推挽输出
  */
static void MX_GPIO_Init(void)
{
  GPIO_InitTypeDef GPIO_InitStruct = {0};

  /* 使能 GPIOC 的时钟：不使能，后面写寄存器一律无效（引脚不会有任何反应） */
  __HAL_RCC_GPIOC_CLK_ENABLE();

  /* 初始输出高电平 = 板载 LED 灭（低电平点亮，见 2.5 节） */
  HAL_GPIO_WritePin(GPIOC, GPIO_PIN_13, GPIO_PIN_SET);

  GPIO_InitStruct.Pin   = GPIO_PIN_13;
  GPIO_InitStruct.Mode  = GPIO_MODE_OUTPUT_PP;    /* 推挽输出 */
  GPIO_InitStruct.Pull  = GPIO_NOPULL;            /* 输出模式不需要上下拉 */
  GPIO_InitStruct.Speed = GPIO_SPEED_FREQ_LOW;    /* 2 MHz，PC13 最高只允许 2 MHz */
  HAL_GPIO_Init(GPIOC, &GPIO_InitStruct);
}
```

  }

{

## 5. 逐段解释

### 5.1 `HAL_Init()` 做了什么

三件事，都能在调试器里验证：

1. 把 SysTick 定时器配成 **每 1 ms 中断一次**，并把 `uwTick` 这个全局变量作为毫秒计数器。`HAL_Delay(500)` 就是靠它实现的——本质是「记下当前 `uwTick`，然后死等直到 `uwTick` 涨了 500」。
2. 设置 NVIC 的优先级分组。HAL 默认用 **分组 4**（4 位全是抢占优先级，没有子优先级）。这一条后面讲中断时要用到，第 3 周的 NVIC 就是从这里接下去的。
3. 调用 `HAL_MspInit()`——也就是上面那个生成 `__HAL_AFIO_REMAP_SWJ_NOJTAG()` 的函数。**这是整章最重要的一句话**：它决定了我的调试口还在不在。

顺带一个坑：`HAL_Delay()` 是**阻塞**的。这里延时 500 ms，意味着这 500 ms 里 CPU 什么都不能干，只是空转等计数器。以后跑 PID 的时候绝对不能用它——闭环需要固定周期、不能被打断，那时候要用定时器中断。这一章的用法只是因为「闪灯」不需要精度。

### 5.2 `SystemClock_Config()` 里每个字段在改哪个寄存器

| HAL 里的字段 | 实际改的东西 | 我的值 / 结果 |
|---|---|---|
| `OscillatorType = RCC_OSCILLATORTYPE_HSE` | `RCC_CR` 的 HSEON 位 | 打开外部晶振 |
| `HSEState = RCC_HSE_ON` | 同上 | 晶振起振，起振失败会卡在这里等超时 |
| `HSEPredivValue = RCC_HSE_PREDIV_DIV1` | `RCC_CFGR` 的 PLLXTPRE 位 | HSE 8 MHz 不二分频，直接进 PLL |
| `PLL.PLLSource = RCC_PLLSOURCE_HSE` | `RCC_CFGR` 的 PLLSRC 位 | PLL 的输入取 HSE 而不是 HSI（HSI 精度差，串口容易出偏差） |
| `PLL.PLLMUL = RCC_PLL_MUL9` | `RCC_CFGR` 的 PLLMUL 位 | 8 MHz × 9 = **72 MHz** |
| `SYSCLKSource = RCC_SYSCLKSOURCE_PLLCLK` | `RCC_CFGR` 的 SW 位 | 系统时钟从 PLL 来 |
| `AHBCLKDivider = RCC_SYSCLK_DIV1` | `RCC_CFGR` 的 HPRE 位 | HCLK = **72 MHz** |
| `APB1CLKDivider = RCC_HCLK_DIV2` | `RCC_CFGR` 的 PPRE1 位 | PCLK1 = **36 MHz**（APB1 上限） |
| `APB2CLKDivider = RCC_HCLK_DIV1` | `RCC_CFGR` 的 PPRE2 位 | PCLK2 = **72 MHz** |
| `FLASH_LATENCY_2` | `FLASH_ACR` 的 LATENCY 位 | 2 个等待周期（72 MHz 必需） |

注意这里**没有**一个字段是「定时器时钟 ×2」——那是硬件行为，不需要我配。当 PPRE1 不等于 /1 时，芯片自动把定时器的时钟再 ×2，所以 TIM2 拿到 72 MHz。第 4 章算 PWM 会用到。

### 5.3 `MX_GPIO_Init()` 里的顺序为什么不能反

```c
__HAL_RCC_GPIOC_CLK_ENABLE();                       /* 1. 先开时钟 */
HAL_GPIO_WritePin(GPIOC, GPIO_PIN_13, GPIO_PIN_SET);/* 2. 先定电平 */
GPIO_InitStruct.Mode = GPIO_MODE_OUTPUT_PP;         /* 3. 再配模式 */
HAL_GPIO_Init(GPIOC, &GPIO_InitStruct);
```

三处讲究：

- **第 1 步必须在最前面**。STM32 每个外设都有独立的时钟开关，默认全部关闭以省电。GPIOC 的时钟不开，`CRH` 寄存器写进去也不生效，引脚不会有任何变化——这是新手最常见的一种「代码明明对但没反应」。
- **第 2 步先写电平再配模式**，是为了避免切换瞬间的毛刺。如果在配置成输出之后再写电平，在配置完成到写电平之间会有一小段引脚处于「刚上电的默认电平」，如果那里接的是电机驱动，这一下就可能动一下。
- **`Push = GPIO_NOPULL`**：输出模式下引脚已经被内部的 PMOS/NMOS 主动驱动，上下拉没有意义。上下拉是给**输入**用的——第 3 周的按键（PA0 下拉、按下为高）就会用到。

### 5.4 `USER CODE` 区：为什么我不能把代码写在别的地方

CubeMX 生成的每个文件里都有成对的记号，光看名字就能猜到该把哪段代码放哪儿：

```c
/* USER CODE BEGIN Includes */   ... /* USER CODE END Includes */   /* 自己 include 的头文件 */
/* USER CODE BEGIN 0 */          ... /* USER CODE END 0 */          /* 自己的函数、变量 */
/* USER CODE BEGIN 1 */          ... /* USER CODE END 1 */          /* 进 main() 后、HAL_Init() 之前 */
/* USER CODE BEGIN 2 */          ... /* USER CODE END 2 */          /* 外设初始化完、进主循环之前 */
/* USER CODE BEGIN WHILE */      ... /* USER CODE END WHILE */      /* while(1) 之前 */
/* USER CODE BEGIN 3 */          ... /* USER CODE END 3 */          /* 主循环体里 */
/* USER CODE BEGIN 4 */          ... /* USER CODE END 4 */          /* 自己写的函数实现 */
/* USER CODE BEGIN 6 */          ... /* USER CODE END 6 */          /* USE_FULL_ASSERT 里的断言 */
```

编号不是连续的（1、2、3、4、6），这是 CubeMX 模板的固定编号，不是我写漏了。我需要特别注意两个位置：**主循环体里要写在 `BEGIN 3` 和 `END 3` 之间**——`BEGIN WHILE` / `END WHILE` 包住的是整个 `while(1)` 结构本身，两个标记之间只夹了一句 `/* USER CODE END WHILE */`，我第一次看的时候以为循环体也归它管。另外，**中断服务函数我不直接去改 `stm32f1xx_it.c`**（那个文件里的标记是按中断名生成的，比如 `USER CODE BEGIN EXTI0_IRQn 0`），而是在 `USER CODE BEGIN 4` 里重写 HAL 给的回调函数（如 `HAL_GPIO_EXTI_Callback()`），这样即使以后重新生成 `stm32f1xx_it.c`，我的逻辑也不会受影响。

规则只有一条：**我自己写的每一行，都必须在这对记号之间。**

原因是 CubeMX 是「重新生成」而不是「增量修改」。我以后每次回去改配置（加一个定时器、改一个引脚），它都会拿模板把 `main.c` 里 `USER CODE` 区**之外**的内容整体重写。写在外面的代码，下一次生成就没了——不是出错，是**悄无声息地消失**，而且如果我不看 git diff，可能要编译失败才发现。

我现在养成两个习惯：① 只在 `USER CODE` 里写；② 每次重新生成代码后，先看一遍 diff 再编译。

### 5.5 Keil 工程里的两个宏

Keil 的 `Options for Target → C/C++ → Define` 里通常写着：

```text
USE_HAL_DRIVER, STM32F103xB
```

- `USE_HAL_DRIVER`：告诉 `stm32f1xx.h` 把 HAL 库的头文件包进来。
- `STM32F103xB`：告诉 CMSIS 我用的具体型号（F103 中容量、64 KB Flash / 20 KB SRAM）。这个宏选错，寄存器的地址映射和中断向量表就可能对不上——症状是「编译能过，跑起来完全不对」，比报错更难受。

这两个宏是 CubeMX 按我选的芯片自动填的，一般不用手改；但如果我手动换过器件型号，一定要回来核对。

### 6.1 坑一：SYS Debug 没设成 Serial Wire，第二次烧录连不上芯片

**现象**：第一次编译下载都成功，LED 也正常闪。改了代码想再下载一次，Keil 弹出：

```text
No target connected
Error: Flash Download failed - Target DLL has been cancelled
```

板子还在通电，线一根没动，但就是连不上。

**原因**（这一条是整章最值得记住的）：PA13 和 PA14 是**普通 GPIO 引脚**，复位后默认被调试外设占用（SWJ_CFG 复位值是 000，即 JTAG + SW 全开）。如果 CubeMX 里 `SYS → Debug` 这一项没有选 `Serial Wire`，生成的 `HAL_MspInit()` 里就不会出现 `__HAL_AFIO_REMAP_SWJ_NOJTAG()` 这句，PA13/PA14 也就没有被明确保留。这时如果把这两个脚配成了别的功能（比如输出、或者别的复用功能），程序一烧进去、芯片一复位，固件立刻按新配置接管了这两个脚——**调试口从物理上就消失了**。而我想改程序又只能通过这个调试口，于是形成死循环：**唯一能救它的手段，被它自己关掉了。**

**怎么定位出来的**（这是判断的关键，不能靠猜）：不是「换个线试试」，而是顺序排除——

1. 板子电源灯亮着 → 供电没问题；
2. 万用表量 SWDIO→PA13、SWCLK→PA14、GND→GND 三点通断 → 接线没问题；
3. 把 ST-Link 的 SWD 时钟从 4 MHz 降到 1 MHz，偶尔能连上 → 说明**电气链路是通的，只是握手窗口太窄**，指向「芯片一复位就立刻把 SWD 脚改掉了」这个方向；
4. 回头看 CubeMX 的 `.ioc` 里 SYS Debug 那一项 → 确认问题在这里。

**解法**，按尝试顺序：

| 办法 | 做法 | 说明 |
|---|---|---|
| ① 复位瞬间连 | 按住板子的 RESET 键 → 在 Keil 里点 Download → 松开 RESET | 芯片还在复位态时，引脚还没被我的代码接管，这个窗口里能连上 |
| ② Connect under Reset | Keil：`Options for Target → Debug → Settings → Debug` 页，把 `Connect` 改成 `under Reset`；再把 `Max Clock` 从默认降到 1 MHz（或 500 kHz） | 让 ST-Link 主动控住复位再连，比手按可靠 |
| ③ 用 STM32CubeProgrammer | 选 ST-LINK 模式，`Mode` 选 `Under reset`，先 `Full chip erase` 把 Flash 擦干净 | 芯片擦空后从系统存储器启动，一定连得上；擦完回到 CubeMX 把 Debug 改成 Serial Wire、重新生成、重新下载 |
| ④ 走 BOOT0 | 把 BOOT0 跳到 1（高电平）、复位，芯片从**系统存储器里的出厂 Bootloader** 启动，这个 Bootloader 不做任何引脚配置，此时用 STM32CubeProgrammer 的 **UART 模式**（接 PA9/PA10）也能擦除 | 这是硬件层面的最后一道保险，SWD 完全没救时用 |

**以后怎么避免**：把「新建工程第二步」固定成 `System Core → SYS → Debug: Serial Wire`，和配时钟一样当成必做项。第 7 节的步骤里我把它写成了单独一步，就是为了不忘。

> 🔬 上面的解法里，①②③④ 我都还没有在真机上走一遍。上机时我会按 ①→②→③ 的顺序试，把实际报错和生效的那一步写回这里。

### 6.2 坑二：Keil 报找不到 `core_cm3.h`

**现象**：CubeMX 生成了工程，双击 `MDK-ARM/*.uvprojx` 打开，一按 Build 就报：

```text
..\Core\Inc\stm32f1xx.h: error:  #5: cannot open source input file "core_cm3.h":
No such file or directory
```

（真实报错前面会带一个行号，不同版本的 `stm32f1xx.h` 行号不一样，我这里不写死。）

**原因**：先要分清两类文件——**CubeMX 生成进我工程里的**，和**器件支持包带来的**：

| 文件 | 谁提供的 | 作用 |
|---|---|---|
| `main.c`、`stm32f1xx_hal_msp.c`、`stm32f1xx_it.c` | CubeMX 生成到 `Core/` | 我的代码、外设底层初始化、中断入口 |
| `system_stm32f1xx.c`、`startup_stm32f103xb.s` | CubeMX 跟着工程复制过来 | 复位后设向量表、给 `SystemCoreClock` 赋值；启动文件里的中断向量表 |
| **`core_cm3.h`** | **器件支持包（Device Family Pack, DFP）里的 CMSIS 组件** | Cortex-M3 内核的寄存器定义（`__NVIC_*`、`SysTick` 等） |
| Keil 的器件数据库、Flash 编程算法 | DFP | 让 Keil 认识 `STM32F103C8`，知道怎么擦写它的 Flash |

所以现象是：**我装了 Keil（IDE + 编译器），但没装 STM32F1 系列的器件支持包**。后果是一串连锁反应——

- `stm32f1xx.h` 里 include `core_cm3.h` 的那一行断了，编译器从这里开始报错；
- 因为读不到 CMSIS 头，`SystemCoreClock`、`__NVIC_SetPriority()` 这类名字全部跟着报「未定义」，所以**屏幕上会有一大串报错，但根因只有一个**；
- `Options for Target → Device` 里看不到 `STM32F103C8`，`Flash Download` 里的编程算法也选不出来。

**怎么定位出来的**：Keil 只报「找不到头文件」，很容易以为是路径问题。判断方法是**看这个文件属于谁**：如果是我自己写的头文件找不到 → 查 `Options for Target → C/C++ → Include Paths`；如果是以 `core_`、`startup_`、`system_` 开头的文件找不到 → 先怀疑器件支持包没装。这是两条不同的排查线，走错了会一直在调路径。

**解法**：装器件支持包，两种方式都行——

1. **在线装**：Keil 里 `Project → Manage → Pack Installer`（或工具栏的 Pack Installer 图标）→ 左侧 `Devices` 找 `STMicroelectronics → STM32F1 Series → STM32F103`，右侧 `Packs` 里找到 `Keil::STM32F1xx_DFP` → 点 `Install`。
2. **离线装**：从 Keil 的器件包页面下载 `Keil.STM32F1xx_DFP.<版本>.pack`，双击安装（它本质是个压缩包，Keil 会自动识别）。

装完后**重新生成/重新打开工程**，让 Keil 重新解析器件。判断装成功的最快方法：`Options for Target → Device` 里能正常看到 `STM32F103C8`，而不是一片空白。

### 6.3 坑三：代码写在 `USER CODE` 外面，重新生成就没了

**现象**：我在 `main()` 的 `while(1)` 里写了四行点灯逻辑，功能正常。后来回 CubeMX 把 PC13 的速度从 Low 改成 Medium，重新 `GENERATE CODE`，回到 Keil 一编译——我写的那四行**不见了**，工程变回了刚生成的空壳。

**原因**：CubeMX 的代码生成是**模板重写 + 保护标记**：它把模板渲染成完整文件，但遇到 `/* USER CODE BEGIN xxx */` 和 `/* USER CODE END xxx */` 之间的内容时，会把上一次生成时的这块内容原样搬过来。标记之外的一切，都按模板重新写一遍。所以这不是 bug，是我用错了地方——我以为 CubeMX 是「只改它自己关心的那几行」，其实它是**整文件重写**。

**怎么定位出来的**：看 Keil 的编译结果和 git 的 diff。**这里有一个很重要的教训**：如果不是我每改一次都提交一次，我根本不会发现代码是「被删掉」还是「我记错了」。所以第 7 节的步骤里我专门写了一条「每次重新生成代码后先看 diff」。

**怎么避免**：

| 做法 | 说明 |
|---|---|
| 只用 `USER CODE` 区 | `BEGIN` 和 `END` 之间是 CubeMX 承诺保留的地方，在这两者之间写就安全 |
| 重新生成后先看 diff，再编译 | 用 `git diff` 或 Keil 里的版本对比。这一步花 10 秒，能省掉半小时的「我刚才明明写了」 |
| 逻辑多一点就单独开文件 | 超过几十行、或者跟 CubeMX 的配置无关的代码（协议解析、PID 计算），放到 `Core/Src/` 下自己新建的 `.c` 里，只从 `USER CODE` 区调用它。这样重新生成完全不影响 |

### 6.4 坑四：山寨 ST-Link 报 "No target connected"

**现象**：Keil 一点 Download 就报 `No target connected`；或者插上后 Keil 弹出「ST-Link 固件需要升级」，点了升级又失败。

**原因**：零售 ¥10~20 的 ST-Link V2 几乎都是仿制的，常见两种情况——

1. **固件版本旧**：芯片里烧的是很早的 ST-Link 固件，新版 ST 工具（含 Keil 的 ST-Link 驱动）会提示升级。但山寨板的 MCU 往往不是原厂 STM32F103C8，或者容量更小，**升级过程写进去的固件超过它的容量就会失败**，失败后调试器可能就废了。
2. **电气/接线问题**：SWD 线太长（>20 cm 的杜邦线）、排针接触不良、没有共地、或者把 ST-Link 的 3.3 V 和 5 V 接错。

**怎么定位出来的**：把「软件问题」和「电气问题」分开——Keil 里 `Options for Target → Debug → Settings`，如果 `SW Device` 那一栏能扫出 `ARM CoreSight SW-DP` 并显示 IDCODE，说明**电气链路是通的**，问题在固件/时钟；如果那一栏一直是空的，先在电线上找原因。

**解法**：

| 现象 | 先试什么 |
|---|---|
| 完全连不上，SW Device 一片空白 | 只接 3 根线先试：SWDIO→PA13、SWCLK→PA14、GND→GND（板子用 USB 独立供电）。确认共地、杜邦线换短一点（≤10 cm） |
| 有时能连有时不能 | `Max Clock` 从 4 MHz 降到 **1 MHz 或 500 kHz** |
| 弹出固件升级对话框 | **先别急着升级**。山寨板升级失败率不低；先在低时钟 + `Connect under Reset` 下试能否正常下载，能用就不动它 |
| 一定要升级 | 用 STM32CubeProgrammer 自带的 **Firmware upgrade** 走一遍（比 Keil 里弹的那个更完整），升级失败再考虑换一个原装或口碑好的版本 |
| 驱动装不上 | 先装 **STSW-LINK009**（ST-Link USB 驱动）；Windows 11 上装不上时，用 STM32CubeProgrammer 的安装包，它会一并把驱动装上 |

> 🔬 这几条我还没在真机上试。上机后我会把「设备管理器里的设备名」「Keil Settings 里的 IDCODE」「最终哪一条生效」记回这里。

### 6.5 坑五：Keil 报找不到 Arm Compiler 5

**现象**：工程打开正常，一 Build 就报类似 `Arm Compiler 5 is not installed`、或提示当前配置的编译器不可用。

**原因**：CubeMX 的 `Toolchain/IDE` 里选 `MDK-ARM V5` 时，生成的工程按 **Arm Compiler 5（armcc）** 配置。但 Keil MDK 从 5.37 版之后**默认不再附带 Arm Compiler 5**（改用 Arm Compiler 6，即 armclang）。于是「CubeMX 生成的配置」和「我装的 Keil」对不上。

**解法**（两条路，选一条）：

1. 去 Keil 官网单独装 **Arm Compiler 5**（作为 legacy 组件），装完在 `Options for Target → Target → ARM Compiler` 里选 5；
2. 把工程的编译器切到 **Arm Compiler 6**：`Options for Target → Target → ARM Compiler` 选 `Use default compiler version 6`，然后 `Rebuild all`。

注意第 2 条不是「改一下下拉框就完事」：AC5 和 AC6 是两套编译器，对旧语法的容忍度不同，可能会冒出新的告警。我自己的做法是——**改完必须 Rebuild 全编译，把新出现的告警逐条看完**，不能只看「0 error」就放心。

> 🔬 这条我还没验证过（取决于我最终装到的 MDK 版本，以及 CubeMX 生成时选的是 V5 还是 V6 工具链）。上机后我把自己那条路的实际操作和报错补在这里。

### 6.6 坑六：串口助手看不到 COM 口

**现象**：把 USB-TTL 模块插到电脑上，设备管理器里出现一个带黄色感叹号的「USB2.0-Serial」或未知设备，串口助手的端口列表里空空如也。

**原因**：国产 USB-TTL 模块绝大多数用 **CH340** 芯片，Windows 10/11 不自带它的驱动，必须自己装。CP2102、FT232 也是同理，各装各的。这一点跟 STM32 完全无关，是「电脑和 USB 转串口芯片」之间的事。

**解法**：去芯片厂商官网（WCH 沁恒）下载 **CH341SER** 驱动安装，装完重新插拔模块；设备管理器里出现「USB-SERIAL CH340 (COMx)」，记住那个 `COMx`，在串口助手里选它，参数设 115200 8N1。

**顺手会踩的第二个坑**：装好驱动、能收到字了，但**全是乱码**。乱码排三件事，按顺序来：① 波特率对不对（两边必须一样，115200）；② 芯片时钟对不对（HSE 没起振时 PLL 会退回 HSI，波特率就偏了——这也是为什么点灯要先跑通）；③ 波特率、时钟都对还乱码，再看电平（是不是接了个 5 V 甚至 RS-232 电平的模块）。

## 7. 复现步骤

下面每一步都写到「点哪个菜单、填什么数字」。所有安装路径**都要求纯英文、不含空格**——路径里有中文或空格，后续工具链调用时会出问题，而且报错信息通常看不出来是这个原因。

### 7.1 装 STM32CubeMX 6.x（含 Java 运行时和 F1 软件包）

1. 到 ST 官网（st.com）搜索 `STM32CubeMX`，进入产品页 → `Get Software` → 下载 Windows 版安装包（`SetupSTM32CubeMX-6.x.x.exe`，或带 JRE 的压缩包）。
   > ⚠️ 下载需要 ST 账号（免费注册）。这一步在浏览器里完成，不是在本仓库里做。
2. 运行安装包。安装向导会先问 Java：
   - 如果电脑里已经有 Java 8 或更高版本，可以选 `Use local Java`；
   - **不确定就选安装包自带的 JRE**（向导里那条「install JRE」的选项）。CubeMX 界面出不来、卡在启动画面，十有八九是 Java 的问题。
3. 安装路径填成纯英文，例如 `D:\STM32\STM32CubeMX`。**不要放在「桌面」「文档」这类路径下**（`C:\Users\33873\Desktop\` 里有用户名，如果用户名是中文就麻烦了——我的机器正好踩在这个边界上，所以我把工具都装到 `D:\` 下）。
4. 装完启动 CubeMX，首次启动会要求用 ST 账号登录（在线校验）。
5. **下载芯片软件包**：菜单 `Help → Manage embedded software packages` → 在弹出的窗口里找 `STM32Cube MCU Package for STM32F1 Series` → 展开选最新版本（`STM32Cube_FW_F1_V1.8.x` 之类）→ 点 `Install Now`。
   > ⚠️ 这一步最容易漏。只装了 CubeMX 而没装 F1 软件包时，新建工程会在生成代码阶段报「找不到固件包」。确认方法：左边列表里 STM32F1 那一行的状态是绿色 `Installed`。

### 7.2 装 Keil MDK-ARM 5.x

1. 到 Keil 官网下载 **MDK-ARM**（免费版是 `MDK-ARM Community`）。社区版对个人学习免费，有 **32 KB 代码大小限制**——我这一章的工程只有几 KB，F103C8 的 64 KB Flash 也远没到限制，够用。
2. 安装到纯英文路径，例如 `D:\Keil_v5`。安装过程会附带装 Pack Installer、以及一个叫 `ULINK`/`CMSIS` 的基础组件。
3. 装完打开 Keil（`μVision5`），按提示用 Keil 账号激活社区版许可（需要联网 + 注册）。
4. **装器件支持包**：`Project → Manage → Pack Installer` → 左侧 `Devices` 里展开 `STMicroelectronics → STM32F1 Series → STM32F103`，右侧 `Packs` 选 `Keil::STM32F1xx_DFP` → `Install`。
   没有网络时，先下载 `Keil.STM32F1xx_DFP.<版本>.pack`，双击安装。
5. 验证：`Project → New µVision Project`，弹出的器件选择框里能搜到 `STM32F103C8` 就算装好了（验证完取消，不要真的新建）。

### 7.3 装 ST-Link V2 驱动

1. 先装 **STM32CubeProgrammer**（ST 官网免费下载）。它自带 ST-Link 的 USB 驱动，后面排查「锁芯片」也要用它，一并装了省事。
2. 如果单独装驱动，去 ST 官网搜 **STSW-LINK009**（ST-LINK USB driver），下载安装。
3. 把 ST-Link V2 插到电脑 USB 口，打开设备管理器：
   - 出现 `STMicroelectronics STLink dongle` 或 `STM32 STLink` → 驱动正常；
   - 出现带黄色感叹号的未知设备 → 右键 `更新驱动程序 → 浏览我的电脑 → 指向驱动目录`；装不上就先装 STM32CubeProgrammer 再试。
4. 接线（4 根杜邦线，长度 ≤10 cm 更好）：

   | ST-Link V2 引脚 | 板子引脚 | 说明 |
   |---|---|---|
   | SWDIO | PA13 | 数据线 |
   | SWCLK | PA14 | 时钟线 |
   | GND | GND | **必须接**，共地 |
   | 3.3V | 3V3 | 供电/电平参考。我打算板子单独用 USB 供电，ST-Link 的 3.3 V 只作电平参考 |

   > ⚠️ 不要接 5 V。板子上 5 V 的脚只能用于给外部模块供电，不能拿来当调试口电平。

   > 🔬 「板子 USB 供电 + ST-Link 只接 4 线」这个接法我还没实测。如果出现连不上，我的下一步是只接 SWDIO / SWCLK / GND 三根线（板子继续用 USB 供电）再试一次，因为部分山寨 ST-Link 需要用 3.3V 那一根来检测目标电压。

### 7.4 装串口助手

三种都行，我建议先备一个独立的（不依赖别的软件）：

| 工具 | 说明 |
|---|---|
| **SSCOM** | 免安装的小工具，常见于国内教程。能收能发、支持定时发送、能存日志 |
| **XCOM** | 正点原子提供的串口调试助手，界面直观 |
| **VS Code 的 Serial Monitor 扩展**（微软的 Serial Monitor） | 我平时就在 VS Code 里写笔记，装个扩展能少开一个窗口；也支持直接输入发送 |

参数统一设成：**波特率 115200、数据位 8、停止位 1、校验 None、流控 None**。

USB-TTL 接线（和 ST-Link 是两套独立的线，别搞混）：

| USB-TTL 模块 | 板子 |
|---|---|
| TX | PA10（USART1_RX） |
| RX | PA9（USART1_TX） |
| GND | GND |
| 3V3 | 不接（板子自己有电） |

> ⚠️ 只接 TX/RX/GND 三根时，模块和板子各自供电。**不要**把模块的 3.3 V 输出也接到板子的 3V3 上，两路电源并联容易出问题。

> ⚠️ 这一章的实验**用不到串口**（只点灯）。装它是因为第 05 章要用，而装驱动常常会卡住，提前搞定，别到时候卡在这一步。

### 7.5 用 STM32CubeMX 建立第一个工程（完整步骤）

这是本章的核心，我把界面路径写全，照着点就能生成出一模一样的工程。

**第 1 步：新建工程、选芯片**

1. 启动 CubeMX → `File → New Project`（或首页的 `ACCESS TO MCU SELECTOR`）。
2. 在 `Part Number` 搜索框里输入 **`STM32F103C8Tx`**，在列表里选中它（封装 LQFP48，Flash 64 KB，SRAM 20 KB）。
   > ⚠️ 不要选成 `STM32F103C8` 以外的相近型号（比如 C6、CB），引脚数和 Flash 不一样，后面仓库里的引脚分配就对不上了。
3. 点右上角 `Start Project`。

**第 2 步：配 RCC（外部晶振）**

1. 左侧 `System Core → RCC`。
2. `High Speed Clock (HSE)` 选 **`Crystal/Ceramic Resonator`**（板上焊的是石英晶振，不是外部有源时钟）。
3. `Low Speed Clock (LSE)` 保持 `Disable`（最小系统板上没有 32.768 kHz 晶振；以后要用 RTC 再说）。

**第 3 步：配 SYS 的 Debug —— 这一步不做会锁芯片**

1. 左侧 `System Core → SYS`。
2. `Debug` 选 **`Serial Wire`**。
3. 顺带看一眼 `Timebase Source`，保持 `SysTick` 即可。
   > ⚠️ **这一步就是 6.1 节那个坑的解药。** 选 `Serial Wire` 之后，生成的 `stm32f1xx_hal_msp.c` 里会出现 `__HAL_AFIO_REMAP_SWJ_NOJTAG()`，PA13/PA14 被明确保留给 SWD。选 `Disable` 就不会有这句，PA13/PA14 有可能被别的功能占用，烧一次就连不上了。

**第 4 步：配时钟树（Clock Configuration）**

1. 切到上方的 `Clock Configuration` 标签页。此时 `Input frequency` 显示 `8 MHz`（来自第 2 步的 HSE）。
2. 按下面这张表填，让界面最终显示 HCLK = **72 MHz**：

   | 界面上的项 | 填什么 | 结果 |
   |---|---|---|
   | `Input frequency` | 8 MHz（HSE 晶振频率，自动带入） | — |
   | `PLL Source Mux` | HSE | PLL 输入 = 8 MHz |
   | `PLLMul` | **×9** | PLL = 72 MHz |
   | `System Clock Mux` | PLLCLK | SYSCLK = 72 MHz |
   | `AHB Prescaler` | /1 | HCLK = 72 MHz |
   | `APB1 Prescaler` | **/2** | APB1 = **36 MHz**（上限） |
   | `APB2 Prescaler` | /1 | APB2 = 72 MHz |
   | `Flash Latency` | 2（界面会根据 HCLK 自动给） | 2 个等待周期 |

3. 填完检查界面右下角的提示：如果某一项超出上限，CubeMX 会用红色标出来，**不允许继续生成**——这是一道免费的检查，别绕过它。

**第 5 步：配 GPIO**

1. 切到 `Pinout & Configuration` 标签页，在芯片图上找到 **PC13**，左键点击 → 选 `GPIO_Output`。
2. 左侧 `System Core → GPIO` → 点 `PC13`，右侧参数设成：

   | 参数 | 值 | 理由 |
   |---|---|---|
   | `GPIO output level` | **High** | 高电平 = 板载 LED 灭（低电平点亮） |
   | `GPIO mode` | `Output Push Pull` | 推挽输出，能主动输出高和低 |
   | `GPIO Pull-up/Pull-down` | `No pull-up and no pull-down` | 输出模式不需要上下拉 |
   | `Maximum output speed` | `Low` | 对应 2 MHz，PC13 的上限 |
   | `User Label` | `LED` | 生成 `LED_Pin` / `LED_GPIO_Port` 宏，代码里比 `GPIO_PIN_13` 好读 |

3. （可选，第 2 周再做）把 **PA5** 也点成 `GPIO_Output`，`User Label` 填 `LED_EXT`，接外接 LED 用。

**第 6 步：Project Manager 里选工具链**

1. 切到 `Project Manager` 标签页 → 左侧 `Project`：
   - `Project Name`：填 **`00-blink`**（英文，不用中文和空格）；
   - `Project Location`：填纯英文路径，例如 `C:\Users\33873\Desktop\AI\GITHUB\stm32-learning-notes\code`；
   - `Toolchain/IDE`：选 **`MDK-ARM V5`**；
   - `Min Version`：默认即可。
   > 如果 6.5 节那个「找不到 Arm Compiler 5」的坑找上我，我会把这里改成 `MDK-ARM V6`（如果你的 CubeMX 版本里有这个选项）再对照处理。
2. 左侧 `Code Generator`：勾上 `Generate peripheral initialization as a pair of '.c/.h' files per peripheral`（把每个外设的初始化拆到单独文件，工程大起来之后更好找）。`Copy only the necessary library files` 保持默认。
3. 点右下角的 **`GENERATE CODE`**。
4. 生成完成后，弹出的窗口里点 **`Open Project`**，Keil 会被自动拉起并打开 `00-blink\MDK-ARM\00-blink.uvprojx`。

> ⚠️ 生成之后**不要**手改 `.ioc` 之外的目录结构。`.ioc` 是 CubeMX 的配置源文件，重新生成工程靠它；它丢了，整个配置就重配一遍。

### 7.6 在 Keil 里编译、下载

1. 打开工程后，`Options for Target`（魔术棒图标）里核对三处：
   - `Target` 标签页：器件显示 `STM32F103C8`，`ARM Compiler` 是能用的版本；
   - `Debug` 标签页：右侧选 **`ST-Link Debugger`** → 点 `Settings` → `Debug` 子页确认 `Port` 是 **`SW`**（不是 `JTAG`）→ `Max Clock` 可以先设 **1 MHz**（稳一点，出问题好定位）；
   - `Utilities` 标签页：勾 `Use Debug Driver`，`Settings → Flash Download` 里 `Programming Algorithm` 有 `STM32F10x Med-density Flash`（128 K 那一条是给大容量芯片的，别选错），并勾上 `Reset and Run`（下载完自动运行）。
2. 按 **F7**（或工具栏 `Build`）编译。目标是 **0 error**；warning 也要逐条看。
3. 按 **F8**（`Download`）下载。看到类似下面的输出就是成功了：

   ```text
   Load "…\\00-blink.axf"
   Erase Done.
   Programming Done.
   Verify OK.
   ```

4. `Debug → Start/Stop Debug Session`（Ctrl+F5）可以进调试：在 `while(1)` 里下断点，按 F5 全速跑、看 `uwTick` 的变化——这是验证「SysTick 真的在 1 ms 中断」最直接的办法。

## 8. 自测题（面试可能这么问）

**Q1：为什么 APB1 要分频到 36 MHz？**
A：因为 APB1 总线上外设的**最高工作频率就是 36 MHz**（RM0008 第 7 章的时钟树里写着），而我的 SYSCLK 是 72 MHz 直接经 AHB /1 下来的。不 /2 就是让 USART2/3、I2C1/2、TIM2/3/4 这些外设超频工作。超频不会报错，只会**时序不准**：串口波特率偏移、I2C 超出规格、定时器计数的实际时间和我算的不一样。另外要注意一个容易记错的点：**APB1 预分频不等于 /1 时，定时器时钟会被硬件自动 ×2**，所以虽然 PCLK1 是 36 MHz，挂在 APB1 上的 TIM2 拿到的仍然是 **72 MHz**——第 4 章算 PWM 频率用的是这个数。

**Q2：SWD 和 JTAG 有什么区别，为什么选 SWD？**
A：它们共用同一批引脚（PA13/PA14/PA15/PB3/PB4），由 AFIO 的 SWJ_CFG 位决定怎么分配。JTAG 用 5 根线（TCK/TMS/TDI/TDO/nTRST），支持多器件菊花链；SWD 只用 2 根（SWDIO/SWCLK），可选加 1 根 SWO 做 trace 输出。我选 SWD 有三个原因：① 线少，接错的概率低，接线占用也小；② **省引脚**——切成 SWD 之后，PA15、PB3、PB4 可以拿回来当普通 IO 用，我只有 37 个可用 IO，这三个很值钱；③ 我不需要菊花链。代价是没有 JTAG 那种多器件调试能力，以及理解 SWJ_CFG 这个复用配置——不知道它，就会在第 6.1 节那个坑里出不来。

**Q3：CubeMX 和 HAL 库是什么关系？**
A：**HAL 库是代码，CubeMX 是写这些代码的工具**，两者不是一回事。HAL（Hardware Abstraction Layer，硬件抽象层）是 ST 提供的 C 语言库，把「配置 `RCC_CFGR` 的 PLLMUL 位」这种寄存器操作包装成 `HAL_RCC_OscConfig()` 这样的函数。CubeMX 是一个图形化的**配置器 + 代码生成器**：我在界面上选好芯片、引脚、时钟树，它把这些选择渲染成一份完整工程——包括调用 HAL 的 `SystemClock_Config()`、`MX_GPIO_Init()`，以及启动文件、中断向量表、外设的初始化。所以：**HAL 是我调用的函数库，CubeMX 是替我把这些调用写出来的工具**。我也可以不用 CubeMX，自己从头写 HAL 调用；但那样每次改引脚都要手抄寄存器配置，容易错。

**Q4：`/* USER CODE BEGIN */` 和 `/* USER CODE END */` 之间的代码为什么必须写在里面？**
A：因为 CubeMX 重新生成代码时是**按模板整体重写**整个文件，只把上一次生成时 `USER CODE` 区里的内容原样搬回来。写在标记之外的代码，下次回 CubeMX 改一个配置就会**静默消失**——不报错、不提示，只在我下次编译或者发现功能不对的时候才暴露。这不是它的 bug，是它的工作方式；我一开始不知道，丢过一次代码（6.3 节）。绕开它的正解有两个：要么只写在 `USER CODE` 里，要么把跟配置无关的逻辑放到自己新建的 `.c` 文件里，从 `USER CODE` 区调用。

**Q5：板载 LED 为什么是低电平点亮？外接一个 LED 到 PA5，电阻怎么选？**
A：板载 LED 的阳极通过限流电阻接在 3.3 V 上，阴极接 PC13，所以 PC13 输出**低电平**时两端才有压差、电流才流通。这也顺带解释了为什么 PC13 有 3 mA 电流和 2 MHz 频率的限制（数据手册引脚脚注里写的）——它不是一颗「全能」的 IO。外接 LED 到 PA5（输出 3.3 V）：红色 LED 正向压降约 2.0 V，串 330 Ω 时

```text
I = (3.3 V − 2.0 V) / 330 Ω ≈ 3.9 mA
```

既能看清亮灭，又远低于引脚上限。换 1 kΩ 只有 1.3 mA，会偏暗；不串电阻则电流只由引脚内阻和 LED 动态电阻决定，完全不受控，可能烧 LED 也可能伤引脚。**限流电阻不是「建议加」，是必须加**——详细的算法在第 [03 章](03-电路基础-限流与分压.md)。
