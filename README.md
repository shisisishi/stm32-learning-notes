## 两条线，一起走

我给自己定的原则是：**既要能写控制，也要看得懂板子**。所以这个仓库的产品结构是两条线并行的：

### 🔌 电控线（嵌入式软件 / 控制）

```text
GPIO 点灯  →  定时器 PWM  →  串口通信  →  I2C 外设  →  ADC 采样  →  通信协议  →  PID 闭环
   02            04            05           06           07           10          09
```

海报上电控组的技能要求是「掌握 STM32 各常用外设（定时器、I2C、串口、ADC、PWM）」——
这条线就是逐条对着这个清单打的。

### ⚡ 电路线（硬件）

```text
欧姆定律/分压/限流  →  去耦电容与电源  →  原理图  →  PCB  →  打样焊接
        03                   08            立创EDA
```

对应的要求是「基本电学素养」「参与整车电气架构」。
我的做法是：**先把每个现象背后的电路算清楚**，而不是照着教程连线。

**合计约 ¥70。** 之所以选 F103 而不是 RM 常用的 F407：
F103 的资料最全、最便宜、最适合打基础；外设（GPIO/定时器/串口/I2C/ADC）的**编程模型和 HAL 库 API 与 F407 基本一致**，
基础打牢后再迁移，成本很低。

### 引脚分配

全仓库共用这一套引脚，各章之间不冲突：

| 引脚 | 功能 | 外设 / 模式 | 用在 |
|---|---|---|---|
| **PC13** | 板载 LED | GPIO 推挽输出（**低电平点亮**，因为 PC13 在后备域、灌电流能力只有 3 mA） | [02](docs/02-GPIO与点灯.md) |
| **PA0** | 按键 | GPIO 输入，下拉 | [02](docs/02-GPIO与点灯.md) |
| **PA1** | 电位器 | ADC1_IN1，模拟输入 | [07](docs/07-ADC采样.md) |
| **PA5** | 外接 LED（呼吸灯） | TIM2_CH1，PWM 复用推挽，1 kHz | [04](docs/04-定时器与PWM.md) |
| **PA6** | 舵机信号 | TIM3_CH1，PWM 复用推挽，50 Hz | [04](docs/04-定时器与PWM.md) |
| **PA9 / PA10** | 串口 TX / RX | USART1，115200 8N1 | [05](docs/05-串口通信.md) |
| **PB6 / PB7** | OLED SCL / SDA | I2C1，复用开漏（必须外接上拉电阻） | [06](docs/06-I2C与OLED.md) |

> **为什么舵机和呼吸灯不在同一个定时器上？**
> STM32 同一定时器的所有通道**共享同一个时基**（PSC 与 ARR），所以一个 TIM2
> 给不出「呼吸灯 1 kHz + 舵机 50 Hz」这两个频率。硬要共用，就得把整个 TIM2
> 降到 50 Hz，呼吸灯的载波会跟着掉到 50 Hz。所以拆成 TIM2（呼吸灯）+ TIM3（舵机）。
> 完整推导和两种方案的取舍见 [04 章](docs/04-定时器与PWM.md)。

### 没有硬件时怎么办

硬件到货之前，我调研过两条"纯软件跑嵌入式"的路子。结论先写在前面：
**它们能帮我理解原理，但不能拿来声称"我会 STM32"，所以我直接买了板子。**

| 方案 | 能做什么 | 为什么不够用 |
|---|---|---|
| **[Wokwi](https://wokwi.com/)** 在线仿真 | 支持 STM32F103C8（Blue Pill），有虚拟逻辑分析仪可以抓 UART / I2C / SPI 波形，不用装任何软件 | 它跑的是 **Arduino 框架，不是 HAL 库**；[官方能力表](https://docs.wokwi.com/parts/board-stm32-bluepill)写明 **ADC 只实现了 ADC1 基础转换，CAN / DMA / RTC / IWDG 均未实现** —— 而 RM 的电机（M3508 / M2006 / GM6020）全部走 CAN |
| **[Renode](https://renode.io/)** 开源仿真框架 | 可以跑**真实的 HAL 固件 ELF**，而且**支持 CAN**，理论上最接近真机 | 门槛高：要自己写 `.resc` 平台描述文件、自己搭 `arm-none-eabi-gcc` 工具链，对零基础不友好 |

所以我的选择是：**先花几十块买真板子**（Blue Pill + ST-Link，约 ¥35），
把 Wokwi 留作"手上没板子时验证外设时序"的备用手段。
这个判断本身也是我这周学到的东西之一：**工具的能力边界要先去查清楚，再决定用不用它。**

| 工具 | 版本 | 说明 |
|---|---|---|
| STM32CubeMX | 6.x | 时钟树配置、引脚分配、生成工程 |
| Keil MDK-ARM | 5.x | 编译下载（社区版免费，32KB 限制足够） |
| 串口助手 | — | 看 printf 输出 |
| [Wokwi](https://wokwi.com/) | 在线 | 无硬件时验证外设逻辑（能力边界见下文） |
| 任意 C 编译器 | gcc / clang / MSVC | 编译 [`code/06-pid-sim`](code/06-pid-sim) 的 PID 仿真和 [`code/protocol`](code/protocol) 的协议自测——这两个模块不依赖 HAL，不需要开发板 |

> 说明：STM32 的工程代码用 **HAL 库 + CubeMX 生成骨架**，需要用 Keil 或
> `arm-none-eabi-gcc` 编译；而 PID 仿真与协议自测是**纯 C、与硬件无关**的，
> 用任何 C 编译器都能直接跑起来（这也是我能在没有板子的情况下先验证它们的办法）。
